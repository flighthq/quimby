# Quimby — Key Design Decisions

The rationale log for quimby's architecture — why each choice was made, and what was rejected. See [design.md](./design.md) for the concepts and behaviors these decisions shape, and [cli-surface.md](./cli-surface.md) for the command reference.

- **Quimby is a courier, not a post office**: It hand-carries parcels between agents and across the boundary; it does not run a mailroom. There is no standing archive of past work — a handoff is assembled, carried, and dropped. This deletes a whole class of maintenance overhead: no sequence counter, no orphaned artifacts outliving removed agents, no unbounded store to curate. Durable history is git's job.
- **A handoff is one shape, carrying whichever halves exist**: Always a folder — note and/or diff and/or files, with a `meta.yaml` written last as the completion signal. "Pack vs instruction" is not a type distinction, just different contents, so there is one object and one set of verbs to learn.
- **Content-derived names, time in the manifest**: A parcel is `<from>-<contentHash>` — no counter, dedupes identical carries, self-describing. `createdAt` lives in `meta.yaml`, not the name, so identical re-sends stay idempotent instead of piling up; chronology comes from the manifest and the `out/sent/` ledger.
- **The mailbox is an explicit-lifecycle `handoff/` tree — state is a directory level, never a dot-dir**: the mailbox is `handoff/out/{draft,queued,sent}/<recipient>` and `handoff/in/{received,processed}/<sender>-<hash>`, with the live `status/<peer>.md` mirror kept at its own root outside `handoff/`. Making the **state a directory level above the party name** (rather than the earlier dot-prefixed `outbox/.sent`, `inbox/.done`) buys three things: it is self-documenting (the lifecycle reads off the path), it is **collision-safe** (an agent may be named anything — even `queued` or `status` — because the scanner enumerates a fixed known set of state dirs and reads party names only as the leaves, so nothing new is reserved beyond today's `host`/name-validation rules), and it gives one clean glob per tray for "all outgoing" / "all incoming." Direction (`in`/`out`) is grouping, not disambiguation (the states are already directional), kept for the two-tray mental model. `status/` stays **out** of `handoff/` because it is a continuously-overwritten mirror, not a discrete parcel — separating it sharpens the "status is not a parcel" principle.
- **Addressed out tray, content-named in tray**: The two trays answer different questions — "who is this for" (`out/queued/<recipient>`) when authoring, "what did I get and from whom" (`in/received/<sender>-<hash>`) when receiving — so they name parcels differently on purpose.
- **Author-then-publish with an atomic rename closes the partial-write race by construction**: an agent authors a parcel under the **unscanned** `out/draft/<recipient>/`, then publishes it with a single same-filesystem `mv` into `out/queued/`. A directory rename is atomic, so a partial parcel **never appears in `queued/`** — the auto-dispatch double-dispatch / half-written-parcel race is prevented structurally, not by timing. The settle-debounce on `queued/` is deliberately **kept as a cheap fallback** (it protects an agent that writes straight into `queued/`, skipping draft), not ripped out — the layering is: staging prevents the race, debounce is the safety net. This supersedes an earlier `.ready`/completion-marker idea (which needed agent cooperation and a reserved filename); draft-staging needs neither. An atomically-published parcel settles in one cycle, so net latency stays ≤1 poll cycle — no "instant dispatch" claim is made.
- **Non-destructive delivery**: Carry drains a queued parcel only on success, and to an `out/sent/` receipt rather than a delete; a bad address bounces and stays queued. An agent never has to rewrite a parcel because a delivery failed.
- **A verb per movement**: `handoff` moves sideways (agent → agent, or host → agent), `dispatch` enacts an agent's outbox queue, `merge` moves out across the boundary, `assign` sets an agent's task. Handoffs land in the inbox and never clobber `assignment.md`. `handoff` and `dispatch` are separate verbs because the outbox is a distinct mechanism, and because keeping the host the only non-agent source avoids unfulfillable path sources.
- **Directed handoff vs ambient status**: Directed work uses `handoff` (addressed, validated); "to whom it may concern" is `status`, which the server mirrors to every agent and each agent reads on demand (`./agent.sh peers`, then a named peer peek). Broadcast is deliberately not a handoff mode — it would copy into every inbox and make every agent filter, the token cost we are avoiding; ambient status stays a pull, so it never lands in an inbox or forces a read.
- **Agents collaborate freely; user-directed work is a first-class, host-stamped parcel property**: ordinary peer notes remain advisory. When the user explicitly delegates through a supervisor, it authors with `agent.sh delegate`; the outbox carries a `delegated: true` claim, and the trusted host promotes that claim to `userDirected: true` in `meta.yaml`. A host-authored note is stamped directly. Message text never grants authority, so a peer cannot trigger delegation accidentally with a magic prefix. The recipient adopts user-directed work when idle, done, or freshly reset; if it is actively executing a direct user assignment, the delegation is high-priority input to surface rather than permission to silently discard in-flight work.
- **A scaffolded agent-side tool enacts the conventions' mechanics — `agent.sh`, shell not Node, producer not parser**: the generated-CLAUDE.md conventions above own every _judgment_ (whether/when to send, what to record where, how to weigh a peer note), but the _mechanical_ steps they prescribe are fiddly and silent-failure-prone — assignment/status persistence, the atomic publish move, the exact `quimby-attest` block with a correctly-keyed `atCommit`, and the inbox received → processed move. So quimby scaffolds a small coordination tool into every agent dir (`agent.sh` + a Windows `agent.cmd` twin; generated by `@quimbyhq/template`'s `renderAgentScript`/`renderAgentScriptCmd`, written and `chmod +x`'d by the local and remote scaffold paths and regenerated on each launch exactly like `CLAUDE.md`, so a newer tool reaches an existing agent). Because the tool is rewritten fresh on every launch, a rename of it propagates without a rebuild: the older `quimby-agent.sh`/`.cmd` names are **removed** on that regeneration rather than left as compatibility wrappers, so the agent dir always shows exactly the current tool. Four decisions define it. (1) **Mechanics, not judgment** — the tool performs the error-prone steps reliably; the conventions keep every decision, so it never chooses whether to send, only how. (2) **It never crosses the boundary** — `agent.sh` only ever writes the agent's _own_ workspace; carrying a parcel to a peer or out to the user's repo stays the host's job (`quimby dispatch`/`merge`), preserving the courier's boundary. (3) **A POSIX shell script, so it adds zero remote dependency** — it runs where the agent runs, and quimby's guaranteed remote floor is `sh` + `git` + coreutils (git is already a hard remote dep) while Node is **not**: a cheap Ollama/qwen runtime may have no Node, and cheap agents are the point, so a Node tool would either exclude them or force a new remote dep. The `.cmd` twin covers the lone non-POSIX case (a Windows-hosted local agent); it is best-effort and unverified, since every remote sandbox is POSIX and the `.sh` is canonical. (4) **An optimization, never a replacement, and DRY where duplication is fragile** — the host is always the canonical _parser_ of these formats (TypeScript), the agent only ever the _producer_, so there is no second parser to drift, just a producer/consumer contract pinned by a round-trip test; and an agent whose runtime lacks `sh`, or that never got the script, still works by following CLAUDE.md. A Node CLI shipped into the sandbox, or teaching the agent to shell out to the host `quimby`, were both rejected: the first breaks the no-new-remote-dep floor, the second breaches the boundary the courier model rests on.
- **The diff is the wire format across the boundary**: A sandboxed/SSH agent is not a reachable git remote, so the host cannot `git fetch` it. Carrying the diff is what makes cross-agent and agent→host movement possible at all.
- **Squashed merge by default**: Agent commit history is useful context but shouldn't leak into the real repo. The boundary ensures the user curates what enters.
- **Merge mode defaults to `--commits`, because its failure is recoverable and squashed's is destructive**: the built-in default was flipped from squashed to `--commits`. The original reasoning weighted the wrong risk — it treated a _loose remainder_ as the hazard to avoid, and called squashed "the safe median" for capturing everything into one commit. But the failure modes are **asymmetric**: squashed's failure silently collapses an agent's curated history (e.g. 140 real commits) into one mislabeled commit — information _destroyed_, and the seed advances so it's awkward to undo — whereas `--commits`' failure just leaves some files uncommitted, which you commit yourself. A good default minimizes the cost of being wrong, so the default is the one whose failure is recoverable. This bit the author repeatedly: a fresh repo with no config would surprise-squash a high-volume, committing multi-agent workflow ("gather the fruit falling from the tree"). Three properties make `--commits` a safe default now: (1) **commits-only, idempotent** — it pulls only the agent's actual committed commits (`git am`, patch-id-deduped so a re-gather lands nothing new); the uncommitted remainder is **not pulled** — it stays on the agent, reported as a count with a pointer to `--patch`/`--squashed`/`--commits -m`. This is "gather the committed fruit; leave what's still growing," and it makes repeated `merge`s safe. (2) **Never synthesizes a commit** — with no commits to replay and no `-m`, it lands nothing rather than fabricating a generic "Apply work from …" commit (exactly the mislabeled-commit failure being avoided); `-m` is the explicit opt-in to sweep the uncommitted delta into one named commit. (3) **The seed-advance keys on the unpulled remainder** — soft (safe sync, preserves the agent's loose work) when `--commits` left work on the agent, hard otherwise; so pulling from a live worker never interrupts it. Squashed stays the robust choice for a no-commit worker (its whole tree → one commit), reached via `--squashed` or `--auto`. **`--auto`** is the opt-in that picks `commits` when the agent has committed work else `squashed` — deliberately _not_ the default, because its behavior hinges on the agent's commit state (the very thing you often can't predict), reintroducing "did it squash or not?" roulette. The mode stays **configurable like git config** (a `mergeMode` key — now `commits`/`squashed`/`patch`/`auto` — resolved across config layers, settable via `quimby merge … --<mode> --default [--global]` or `quimby merge-mode <mode>`); `--auto --default` persists `auto` (staying adaptive), not the mode it resolved to. Precedence: an explicit flag wins, else the configured default, else `commits`. `--squashed` still exists to override a configured commits/auto default for one merge.
- **A non-zero editor exit cancels the merge, silently**: when a squashed merge opens the commit-message editor (no `-m`), quitting with a non-zero exit (`:cq` in vim) is the user changing their mind — it cancels the merge with nothing landed and nothing printed, mirroring how git itself treats a non-zero editor exit as an abort. This matters because picking the wrong mode is expensive to undo (once a squash lands and the seed advances, re-merging as `--commits` finds nothing), so a clean bail at the decision point is worth having. An empty (but saved) message still reports the abort explicitly; a genuine spawn failure (editor missing, no exit code) still surfaces as a real error — only a completed-but-non-zero editor run is read as an intentional cancel.
- **Merge is a merge, not a patch**: The agent's diff is reconstructed on a temp branch from the seed, then merged into the target — not patched directly onto the working tree. A patch fails when the target has moved past the seed (the common case with multiple agents); a merge handles it with git's 3-way machinery, producing standard merge conflicts the user can resolve with tools they already know. The agent is never touched — no non-working state inside a sandbox. Conflicts live on the host where the user has full tooling. The merge is a **plain, fast-forward-when-possible** merge, deliberately **not** `--no-ff`: when the target hasn't moved past the seed the agent's commit fast-forwards into clean linear history; a merge commit appears only when the target genuinely diverged, and then it is a standard `Merge branch …` node the user recognizes and can rebase away. Forcing `--no-ff` (with a parcel-derived merge message) was rejected because it stamped a same-message work-commit + merge-commit pair onto history for every merge — visual duplication with no upside for a user who prefers the landed work to read as the newest commit.
- **Merge advances the seed by default, but only when it's lossless**: an agent's diff is cumulative (working tree vs `quimby/seed`), so the iterate-one-agent loop — merge, then ask for a revision — otherwise re-carries already-shipped work every round and conflicts the moment the regenerated diff isn't byte-identical to what landed. So a clean, committed `merge` advances the agent's seed onto the merge (`sync -f`), making the next diff incremental; `--no-sync` opts out of the whole alignment (both this advance and the pre-sync — see the pre-sync decision above), and `--sync <ref>` advances _and_ retargets the agent's sync ref to `<ref>` — see the `--sync` decision below. It is deliberately **conditional**, not a blind default, because the advance is a hard reset: it runs only when the merge settled onto the branch the agent tracks (its `syncRef` — not a `-b` landing branch or foreign `-t`, which are deliberate deferrals) **and** the agent hasn't moved since the snapshot the merge captured (equal content hashes ⇒ identical tree ⇒ nothing to lose). Either condition failing leaves the seed untouched with a pointer to the manual `sync --current -f`. This mirrors `assign`'s sync-by-default naming; `merge`'s _pre-sync_ is the same non-destructive rebase as assign's and defaults on for the same reason, but `merge`'s _post-advance_ is a destructive reset, so it earns its default-on only through the two conditions above. The advance's _mechanism_ follows what each mode leaves loose, which resolves the tension between "advance for incremental diffs" and "don't wipe the agent's work-in-progress". **Squashed** commits the agent's whole tree, so nothing is left unlanded — a **hard reset** (`sync -f`) onto the base is lossless, and it stays gated on a fully-committed, no-drift landing. **`--commits`** lands only the commits and leaves the remainder loose, so its advance is a **soft** (safe) sync that stashes/rebases/pops — it advances the seed past the committed part while _preserving_ the uncommitted remainder on the agent. That means `--commits` advances **even with a loose remainder** (the safe sync keeps it, so there's no "incomplete landing" to withhold for), and it drops the no-drift gate (a soft sync tolerates a still-working agent), which is exactly "pull down what a worker produced without interrupting it." A soft advance onto a base other agents moved can hit a genuine rebase/pop conflict — surfaced on the agent to resolve, not silently lost. **`--patch`** (and the no-TTY squashed degrade) commits nothing, so nothing settles and the seed stays put. Whenever the seed is _not_ advanced but a standard merge would have, `merge` prints the catch-up sync so the agent never silently goes stale. The earlier "only a fully-committed landing advances" rule was the right call _while the advance was always a hard reset_ (a `--commits` remainder genuinely couldn't survive one); making the `--commits` advance soft is what lets the remainder be kept and the landing settle anyway.
- **Merge syncs the agent onto the target first, by default — so conflicts resolve on the agent, not your repo**: `merge` used to cross the boundary from the agent's _old_ seed, which made multi-agent landings conflict often. With several agents' work already on the branch, the agent's diff measured against a stale base textually collides with already-shipped work _even where nothing semantically overlaps_ — the cumulative-diff trap one level out (across agents, not across an agent's own revisions), where context/hunk drift flags conflicts on lines the agent never touched. So `merge` now runs the safe pre-sync (`sync`'s non-destructive rebase onto the merge target) _before_ it stages the parcel, advancing the merge base to the branch's current tip. That eliminates the stale-base _false_ conflicts by construction; only genuine same-line overlap survives — the minority case — and it surfaces during the **rebase in the agent's own clone**, which aborts there with the work intact. So a real conflict is resolved on the agent (nudge it to rebase — it has the code context, and the human is the integration bottleneck) instead of landing as a `git merge` left in progress in your real repository. A clean pre-sync then makes the boundary crossing a fast-forward — exactly the condition that fires the lossless post-advance and the clean-landing celebration — so the rewarding loop becomes the common case, not the lucky one. This is the boundary philosophy taken to its end: the mess stays on the agent side, and only resolved work crosses. It reuses `assign`'s graceful degradation — a pre-sync conflict aborts before anything is staged, reports, and points at resolving on the agent then re-running — and, like the post-advance, is **gated on merging into the branch the agent tracks** (skipped for a `-b` landing branch, a divergent `-t`, or an off-`syncRef` HEAD, where rebasing onto `syncRef` would pick the wrong base). Both ends therefore fire together for the ordinary iterate-on-its-branch case and both stand down for the deliberate off-branch merges. The `--sync`/`--no-sync` flag governs **both ends as one concept** (see the `--sync` decision below): bare/default aligns before + advances after, `--no-sync` leaves the agent's base untouched at both ends — which doubles as the raw-merge / resolve-on-the-host escape hatch. The one combination this collapse drops — raw-merge-but-advance-the-seed-anyway, the _old_ default — was deliberately let go: it only existed because pre-sync wasn't a thing, and "cross from a stale base, then hard-reset onto the result" is not a coherent thing to want. Rejected: keeping raw-merge-then-resolve-on-host as the default (it makes the boundary the conflict site and leaves the reward loop to chance); a separate `--presync`/second verb (the one-`--sync` collapse folds it in).
- **A pre-sync rebase conflict falls back to the boundary merge — it doesn't hard-block, because the rebase is a stricter test than the merge**: the pre-sync is a _rebase_ (a per-commit replay onto the moved `syncRef`), while the actual boundary crossing is git's _3-way merge of the net change_. A rebase can conflict on an **intermediate** commit even when the cumulative change merges cleanly — so a hard block on the rebase refuses merges that would land with zero conflicts. This bit a user directly: the default merge refused in every mode with "conflicts with `<ref>`", yet `--no-sync` merged instantly and cleanly — because `--no-sync` skips the rebase and goes straight to the net merge. The mode flags were never the lever (they're downstream of the pre-sync), so cycling `--patch`/`--squashed`/`--commits` all hit the same wall, which read as "merge is broken." The fix keys on **why** the pre-sync failed, carried on `SyncConflictError.agentClean`: a rebase conflict that **rolls back cleanly** (repo intact, `agentClean: true`) is _not_ treated as fatal — `merge` proceeds to stage and attempt the boundary merge, landing like `--no-sync` (seed left put, catch-up hint). Only if the net 3-way _genuinely_ overlaps does a conflict surface, and then `merge` **aborts the tentative host merge and routes back to the agent** — preserving the original "resolve on the agent, not your repo" guarantee for the case that actually warrants it (a real same-line clash), while dissolving the false blocks. The hard block survives **only** for a genuinely **wedged** agent repo (`agentClean: false` — a pre-existing in-progress merge/rebase or unmerged index, a failed rebase-abort, or a post-rebase stash-pop conflict), where the working tree carries markers and can't be safely captured. Rejected: (a) keeping the hard block (the reported bug — refuses clean merges, and only names resolve-on-agent, never `--no-sync`); (b) leaving the conflicted merge in the host on the fallback's genuine-overlap case (that would silently flip the boundary philosophy, dumping the mess on the host — so the fallback aborts and routes to the agent instead); (c) distinguishing the two failure modes by string-matching the error message (brittle — hence the typed `SyncConflictError` with an explicit `agentClean` discriminant, thrown from the one `runSyncAlgorithm` shared by local + SSH).
- **Merge conflict recovery leans on git, with silent staging auto-heal — no `merge --continue/--abort`**: a conflicted `merge` is left in progress for the user to finish with native `git merge --continue`; quimby adds no wrapper command for the in-progress case. For the **abandoned** case (`git merge --abort`, which leaves the staged parcel orphaned), quimby doesn't ask the user to remember a cleanup verb either — the next `merge`, when it stages fresh work, **silently clears** a leftover staging area, gated on there being **no git merge in progress** in the target (an in-progress merge is the live retry path, so its parcel is preserved). Merging an already-staged parcel _by name_ skips the heal, since that path points at staging deliberately. A dedicated `quimby merge --continue/--abort` or a `gc` verb was rejected as ceremony over an auto-heal that costs the user nothing to remember.
- **The boundary never fabricates a commit message**: crossing into the real repo is an explicit, curated act, so the one commit a squashed `merge` creates is authored by the user — git's editor opens prefilled with the agent's own subject (`-m` skips it). `--commits` carries the agent's real commit messages verbatim and leaves any uncommitted remainder loose in the working tree (the agent didn't commit it, so quimby doesn't invent a commit boundary it never drew); `--commits -m` opts that remainder into one named commit. The rule holds even non-interactively: with no `-m` and no TTY there's no one to author the message, so rather than stamp a generic `Merge work from <agent>`, squashed **degrades to `--patch`** — the work still lands, uncommitted, message printed for the user to commit with. This collapses the three modes onto one rule (a landed commit is either the agent's or yours, never quimby's) and makes `--patch` legible as "what squashed becomes when the message can't be authored." The celebratory quip fires only on a fully-committed landing, so success reads as success and an uncommitted landing reads as "more to do."
- **Advisory checks are cooperative — ask, attest, relay; never execute, never gate**: quimby cannot honestly run an agent's build/test check, because it is a host-side courier running _outside_ the sandbox where the deps live. So quimby _asks_ the agent to self-check (`nudge --verify`, `assign --verify`, an agent `verifyByDefault`, or a CLAUDE.md convention), the agent runs its own `check` command (`set <agent> --check`) inside its sandbox and records an **attestation** — a `quimby-attest` block in `status.md` (`command`/`result`/`summary`/`atCommit`) — and quimby **relays** that self-report at the boundary: shown in `status`, printed before `merge`/`handoff`, later embedded in the parcel `meta.yaml`. Quimby never re-runs the check and **never gates** — a failed/absent/stale attestation warns, the human still decides. Because it is a self-report relayed, not a quimby guarantee, the display headline speaks the CLI noun **check** with a **(self-reported)** qualifier carrying the relay honesty — never "verified"/"validated", which would imply quimby ran the check itself. This is the only honest shape: the check runs where the deps are, and the boundary stays the human's call.
- **Assign syncs by default, but never loses the message**: Assigning to a stale agent wastes tokens — the agent works off wrong files, discovers issues that are already fixed, or produces diffs that conflict on merge. `assign` writes `assignment.md` first (the user's intent is durable), then syncs the agent to its base. If sync fails (rebase conflict), the assignment is still on disk — the user's message is never lost — but the nudge is suppressed (don't wake an agent on a stale baseline). The user resolves the conflict and runs `quimby sync` manually. `--no-sync` opts out entirely. `--sync` is a **ref string** here too: `--sync <ref>` retargets the agent's sync ref to `<ref>` and syncs onto it before the assign (citty yields `false` for `--no-sync`, a string for `--sync <ref>`, so one flag carries both the skip and the retarget).
- **One `--sync`, optionally-valued and uniform — not a `--sync`/`--advance` split**: `--sync` used to mean two things — a ref-string on `add`/`set` (the sync root) but a plain boolean on `assign` and `merge`. Rather than split it (an earlier take renamed merge's boolean to `--advance`, which added a second verb to learn), it is kept as **one flag** made **optionally-valued** and given **one meaning everywhere**: bare `--sync`/default is the natural sync (`assign` syncs to the agent's `syncRef`; `merge` syncs the agent onto the target _before_ landing **and** advances the seed _after_ — its "natural sync" is now the whole both-ends alignment, not just the post-advance), `--sync <ref>` names/retargets the sync ref (`add`/`set` set it; `assign` retargets-then-syncs; `merge` retargets `syncRef` to `<ref>` as it advances after — the pre-sync always aligns onto the branch you're merging into, so a ref only points the agent elsewhere going forward), and `--no-sync` skips (for `merge`, leaving the agent's base untouched at both ends — which is also the raw-merge / resolve-on-the-host path). This leans on citty distinguishing "flag present, no value" (bare, `''`) from "present, with value" (the ref) from "negated" (`--no-sync` → `false`); `-s` stays the short form on `add`/`set`. One flag, one mental model, optionally carrying a ref — no new `--advance` verb, and `merge`'s pre-sync and post-advance stay one concept rather than two flags (the one combination this drops — raw-merge-but-advance-anyway — is incoherent in practice; see the merge pre-sync decision above).
- **Server is infrastructure, not convenience**: Agents in sandboxes can't see each other. The server is the only entity with cross-agent visibility. It's architecturally necessary, not a nice-to-have.
- **Status mirrors to every agent; discernment moves to the reading side (pull-on-demand), replacing subscribe**: the server used to route each agent's status only to _subscribers_ (`subscribe`/`unsubscribe`, a `state.subscriptions` map). That was dropped for **always-mirror**: the server writes each agent's `status.md` into _every_ other agent's `status/<name>.md`. The key realization is that the token cost was never the _mirroring_ (status files are tiny — disk, not tokens) but the _reading_. Subscribe bounded reading indirectly, by bounding what got mirrored; always-mirror + **pull-on-demand** bounds it directly — agents don't slurp the whole roster each cycle, they use `./agent.sh peers` and read a peer only when they have a reason (the generated context says so). So mirroring can be universal at near-zero cost, the "forgot to subscribe" silent miss disappears, and the `subscribe`/`unsubscribe` verbs, the state field, and the server's POST/DELETE endpoints all go away. The asymmetry that makes this right: the **human** has unbounded context and sees every agent on demand via `quimby status`; the **agent** is token-constrained, so it gets availability (everything mirrored) with bounded attention (read on demand). The courier split stays sharp: **directed** work is pushed (`handoff` + nudge); **ambient** status is pulled (a peer-status peek) — folding status into re-sent parcels would be chattier and lose the publish-once/pull property.
- **Status mirroring is batched per recipient and reported per source — an N×N fan-out cannot be delivered one round trip at a time**: always-mirror is right (see the decision above) and its _write_ cost really is near-free — but only if the writes are batched. Delivering one file per remote call made the cost N², and on an 8-agent SSH fleet that was ~112 round trips (two each, `ensureDir` then `writeFile`) taking ~16s of every **5s** poll cycle. The cycle runs status → reconcile → auto-dispatch → remind in sequence, so status mirroring was starving the auto-dispatch that actually keeps a fleet moving, and the only symptom was a `Poll cycle still running after 5s — skipped N tick(s)` warning that named the interval rather than the cause. Three changes, and the order of blame matters: the _log_ volume was the visible complaint (N² lines per cycle, 64 for 8 agents, reprinted in full on every restart since first sighting also mirrors), but it was a symptom of the same fan-out. So reads now run concurrently, delivery is **one call per recipient carrying every peer that changed this cycle** (N round trips, not N²), and reporting is **one line per source** naming the peer count. The redundant per-write `ensureDir` goes with it — both transports already create the parent inside `writeFile` (`SSHTransport` as `mkdir -p … && cat > …` in a _single_ command), so the directory guarantee was never what the extra call bought; the batched command keeps an explicit `mkdir -p` in the same invocation, which is strictly stronger than a separate one because no window exists between it and the writes. Payloads travel **base64-encoded on stdin**, never on the command line — the command carries only the target directory and a decode loop, so its length is flat (~170 chars) no matter how large the statuses are. The stdin part is not tidiness: the first cut embedded the base64 _in the command_, and because execa echoes the entire failed command in its error message, one failed delivery dumped ~40,000 characters of payload into a live `quimby serve`. The rule that falls out is general — **anything unbounded belongs on stdin, because a command line is also an error message** — and it is paired with a hard cap on any reason string a log line interpolates. Base64 (rather than raw bytes) keeps the line framing intact for arbitrary status prose containing quotes, `$(…)`, or backticks, none of which can reach the shell from stdin; `base64` is coreutils, inside the guaranteed remote floor. Two invariants are deliberately preserved against the condensation: a **failed recipient is still named individually** with its error, because "delivered, nobody woken" being indistinguishable from a broken courier is the exact failure mode this codebase keeps relearning; and one unreachable host **cannot abort the others' delivery**, which the old serialized loop could do. Rejected: raising `--poll` (hides the cost rather than removing it, and inflates dispatch latency); and mirroring less than everything (that would trade the always-mirror guarantee — and reintroduce the "forgot to subscribe" silent miss — to fix what is really a batching problem).

- **Auto-dispatch enacts the outbox**: while running, the server carries settled outbox drafts to their recipients on the poll cycle — the final removal of the human-as-messenger from the directed channel, since `dispatch` was already agent-authored routing the human merely triggered. It is orthogonal to status mirroring: `dispatch` carries **directed, discrete parcels** (a diff and/or note addressed to one recipient), status mirroring reflects **ambient status**. The safety comes from the same courier invariants automation needs: content-hashed names dedupe, bounces stay queued, `out/sent/` is the ledger — plus the **atomic author-then-publish** (draft → queued via one `mv`) that keeps a half-written parcel out of the scanned queue by construction, a **settle debounce** as the fallback (a queued parcel carries only after its files are unchanged for a full cycle), and an **attempt-once** rule so a bad address never nudges in a loop. Because human-gated dispatch was also the accidental rate limiter against the #1 pain point (token exhaustion), auto-dispatch is opt-out per server run (`--no-dispatch`), never per-agent config.
- **`serve -it` binds the server's life to a terminal, like `docker run -it`**: the server is a background daemon, but running it in one terminal and typing commands in another is friction. `-it` starts the server and stacks a shell on top in the same terminal, so commands run live against the server underneath and the server dies when you leave the shell. Ctrl+C is deliberately **not** a single-press kill — the shell owns it for interrupting commands, and only `exit`/Ctrl+D or a quick **double** Ctrl+C tears the server down, so interrupting a long command never accidentally takes the server with it. The server library returns a `stop()` handle rather than installing its own `process.exit`, so the command layer owns lifecycle in both the plain and interactive modes.
- **`serve --stop` is a flag, not a `stop` subcommand**: a background `quimby serve` (plain, no `-it`) needs a way to be stopped from another terminal without hunting the pid. That lives as `serve --stop` rather than a top-level `quimby stop`, because **`quimby stop` is already the agent verb** (kill an agent's tmux session) — a second meaning would collide. `--stop` reads `server.json`, signals the pid (the server's own SIGTERM handler runs the graceful `stop()`), and removes the pidfile so a stale entry never lingers; a missing/dead server reports cleanly and still sweeps any stale pidfile. The `stopServer` primitive lives in the server package beside `getServerInfo`, so the CLI stays a thin caller.
- **Three interaction modes coexist**: Interactive (run), headless (start), and server (serve) are separate concerns. run/start manage individual agents; serve manages the connections between them.
- **Stable IDs, not names**: `QuimbyState.id` and `AgentState.id` are UUIDs generated at creation and never change. tmux session names are derived from IDs, so renaming an agent doesn't orphan a running session.
- **One UUID is an agent's identity across every surface; the name is only a display label**: an agent's `id` keys its on-disk directory (`.quimby/agents/<id>/`, local and remote), its tmux session (`qb-<projectId[:8]>-<agentId[:8]>`), and its sandbox name. The friendly name is a pure display attribute — stored in `state.yaml`, shown in `quimby list`, and set as the tmux **window** title (`rename-window`) on each `run` so the on-screen label tracks renames. `quimby rename` also pushes the new label onto the agent's **live** window immediately (`renameAgentWindow`), so a running or attached session — and any dashboard tab sharing that linked window — updates in place instead of waiting for the next `run`; a stopped agent simply no-ops. Because nothing on disk or in a live session is keyed by the name, **rename is a pure relabel**: the directory never moves (no `fs.rename`/`mv`), so the sandbox and tmux session bound to that path survive, and no running work is orphaned. Existing name-keyed workspaces migrate on state load (local: `fs.rename` to the id-dir; remote: a guarded `mv` on next `run`).
- **The sandbox name is a path-and-command hash over the UUID-keyed directory**: `sbx` is path-sensitive — it persists the working directory's absolute path behind its `--name` — so the name must track the path, not pin it. It also refuses to reuse a named sandbox for a different base command (for example a sandbox first created for `claude` cannot later run `codex`), so the runtime passes `--name qb-<agentId[:8]>-<hash>`, where the hash covers the project id, agent id, agent directory, and base entrypoint command. Since the directory is UUID-keyed, the path portion is **stable across a rename**, so a same-command sandbox is reused; a genuine **relocation** (the `.quimby` tree moving, or a clone mounted at a different path) changes the absolute path, flips the hash, and lets a fresh sandbox fall out instead of a stale name pointing at a directory that is gone. A real runtime-profile command change (`claude` → `codex`) also flips the hash, avoiding `sbx`'s "already exists and runs ..." collision. This is why a path-and-command hash beats keying the sandbox on the bare UUID: a UUID name would survive rename but go stale on relocation and collide across command changes. The friendly name is deliberately **not** in the sandbox name — it changes on rename and would needlessly break reuse; the `agentId[:8]` prefix is a stable, greppable handle for `sbx ls`. `run` and `exec` still share a sandbox when they use the same base command.
- **Runtime profiles are named launch/provisioning intent, not secrets**: roles answer "what kind of agent is this?"; runtime profiles answer "how should that runtime be launched and checked?". An agent stores only a profile name (`defaults.runtimeProfile`), while layered config resolves the profile at launch/doctor time. When a repository tracks `quimby.yaml`, that file is authoritative for the shared profile/role fields it defines (notably `runtime` and `entrypoint`) because it is visible and reviewable; ignored `.quimby/local.yaml` and user config add local-only names and fill private machine details such as provider hosts, host aliases, env, and credentials-adjacent settings. This keeps the shared launch graph auditable without forcing worker names, IPs, or auth-sensitive values into git. The resolver is its own package: config loading stays dumb, adapters stay focused on command shapes, and both launch and doctor consume the same small selection object (`runtime`, `entrypoint`, `env`, required tools). For SSH agents, those profile requirements are checked on the destination host, because that is where `openshell`, `ollama`, `sbx`, and their auth state actually live.
- **An agent stores its role and resolves launch config fresh; drift is detected on the resolved command, and `restart` applies it**: an agent used to bake its role's runtime profile/entrypoint into a flattened `defaults` at creation, so editing the preset/role/profile later — or _renaming_ a profile — left existing agents pointing at a now-stale (or dangling) name, and a running tmux session kept whatever command it was born with. Two coupled fixes, mirroring the host-alias pattern. (1) **Store the role reference, resolve at launch**: `AgentState.role` records the config role, and `resolveAgentLaunchDefaults` resolves runtime profile/entrypoint from _current_ config through it at every launch (an explicit `--runtime`/`--cmd`/`--runtime-profile` still wins; a role that no longer resolves degrades to the stored `defaults`, never a hard failure). So a profile edit or rename propagates to existing agents with no rebuild — `quimby set <agent> --role <role>` attaches a role to a legacy agent to opt it in. (2) **Drift is the _resolved command_, not the name**: on session create, `launchFingerprint` (a hash of the resolved `runtime`+`entrypoint`) is stored in `AgentState.launchedWith`; `run`/`start` compare it against the freshly-resolved command and _warn_ only when they differ — so a role rename that resolves to the same command leaves the session untouched (no false drift), and a real change surfaces as an advisory pointer to `quimby restart`. Restart is a **dedicated, explicit verb** (`quimby restart <agent…> [--all]`), never automatic and never `run --restart`/`start --restart` (a preset user drives the whole fleet, and a magic auto-restart would silently discard the live session's chat context): it kills the session and relaunches through `start`, so the agent comes back on current config and resumes from `status.md`. The invariant: you only ever lose live context when the command genuinely changed _and_ you chose to restart — the retained-session model is preserved, drift is surfaced, and applying it is one deliberate command.
- **`quimby init` scaffolds config, not a workspace — and prefers referencing what your machine already has**: the old "no init command" rule was about _workspace bootstrap_ (state is created lazily by the first `add`/`up`/`run`, never a mandatory step) and stays true. But it left a real gap the author kept hitting — copying `quimby.yaml` between projects to get a similar shape. That is a _config_ concern, not workspace state, so `init` fills it as the shared-config counterpart to the per-agent `config` walkthrough: it authors a tracked `quimby.yaml` (roles, runtime profiles, a preset, a layout, a `default`) from a built-in **starter** (`solo`/`review-loop`/`fleet`), interactively customizable (engine, builder `count`, location) or by name. It is deliberately the _one_ command whose job is to write the tracked file — everywhere else the tools auto-write only to ignored config, so authoring the shared file stays an explicit, requested act (and it refuses to clobber an existing `quimby.yaml` without `--force`). Two properties make it fit the rest of the design. (1) **It reuses your existing personal config**, uniformly by kind: host aliases already **bound** in your user/local config are offered and written as a _reference_ (`hostAlias: remote`, with `remote` declared unbound in the tracked file) — so an alias you already configured on this machine needs no re-entry and its address never enters git; and runtime **profiles** you already declared are offered as engine choices, referenced by name with only their **shareable shape** (`runtime`/`entrypoint`) inlined into the tracked file while the machine/secret fills (`env`/`provider`/`model`/`ollama`/`permissions`) stay in your private config and merge back at resolution. Aliases are reference-only (an address is inherently per-machine); profiles are shape-inline + secret-reuse (the shape is team-safe, the secret is not) — either way the tracked file never carries a secret, exactly the declare-shared / bind-private split one layer up. (2) **It composes the primitives already shipped**: a starter is just roles × profiles × a `@role` layout × replica `count`, so `init fleet` → `up` → `run` yields a heterogeneous-capable, role-slotted dashboard with no new mechanism. Starters live in `@quimbyhq/workspace` (`buildStarterConfig`, pure) with the clack prompting in the CLI, and the serialized yaml uses fresh per-role objects so it carries no confusing anchors/aliases for a human to edit around.
- **The interactive walkthrough is config-aware and persists references, with one engine authority**: `quimby add` (flag-less) and `quimby config` run an arrow-key walkthrough, and it used to be blind to the config layer — it collected a raw `runtime` enum + free-text `entrypoint` and wrote them as flattened `defaults`. That was doubly wrong once roles/profiles became first-class: it couldn't _offer_ `config.roles`/`runtimeProfiles`/`hosts`, and worse, on a role- or pin-backed agent the launch resolver subordinates `defaults` to the role/pin — so `config`'s edits silently never took effect. The fix makes the walkthrough speak the same layered vocabulary as the flags and persist _references_: it offers declared **roles** as a starting choice, **runtime profiles** as the engine (including pinning one over a chosen role — the interactive twin of `add --profile`), and **host aliases** as the location (storing `{type:ssh, alias}`, with an inline bind for an unbound one), degrading to the raw runtime/entrypoint/host flow only when the config declares none. The load-bearing idea is that the walkthrough returns a **discriminated engine source** (`role` | `profile` pin | `manual`), which a pure `resolveWalkthroughConfig` maps to **exactly one engine authority** — a role reference, a `runtimeProfile` pin, or flattened `defaults` — and `config` writes that authority while _clearing_ the others, so the choice can't be shadowed by a stale snapshot. This also closed a latent inconsistency: `set --runtime-profile` now writes the top-level **pin** (via the new `setAgentRuntimeProfile`) instead of `defaults.runtimeProfile`, so flags and prompts agree that a profile overrides the role. Prompting stays in the CLI (`@clack/prompts`); the coherence mapping is pure and unit-tested apart from the prompts.
- **A host alias is a first-class indirection bound per-machine, never a flattened address**: a tracked `quimby.yaml` can _declare_ a host alias (`hosts: { remote: { host: remote } }` — or simply omit `host`) without committing a private address; the concrete `user@host` is bound per-machine into ignored `.quimby/local.yaml` (default) or user config (`--global`), so it never touches git. The distinction is explicit: an alias whose `host` is absent, empty, or **equal to its own name** (the self-referential placeholder) is **unbound**. Crucially the agent stores the alias _reference_ (`location: { type: ssh, alias: remote }`), not a flattened address — the address is resolved from layered config **at launch**, so binding it once (or rebinding it) propagates to every agent that shares the alias, and a `restore` on a fresh machine reconnects by re-resolving rather than carrying a stale IP. An earlier design flattened the alias to a concrete `location.host` at `add`/`restore` time, which killed the indirection: the stored string was handed straight to `ssh`, `run` never re-consulted config, and a nuked-then-restored workspace baked in a bogus `host: remote` that failed DNS with no way to bind it. Resolution is a pure function (`resolveSSHConnection`), so it also recognizes a **legacy** flattened `host` that happens to name a declared alias and treats it as that alias — the migration is behavioral, not a state rewrite. When an unbound alias is actually needed (a launch, or `restore`'s own scan connection), quimby **prompts once** and persists the answer (interactive only — a non-TTY caller gets a `quimby host <alias> --set …` hint instead of a mystery DNS error), then continues; sibling agents on the same alias resolve without re-asking. Prompting lives in the CLI (`@clack/prompts`) while the resolver/persistence stay pure in `@quimbyhq/workspace`, keeping packages clack-free. `quimby host` is the explicit, scriptable counterpart — list aliases with bound/unbound status, or `--set`/`--global` to bind without launching. The rule mirrors the boundary invariant one level down: the tracked repo declares _intent_ (an alias exists), the private layer supplies the _secret_ (its address), and quimby fills the gap the moment it bites rather than failing opaquely.
- **"Presets" name a saved arrangement; a "default" preset makes bare `quimby up` and `quimby run` do the obvious thing**: the config concept that names a set of agents + a layout was renamed `recipes` → **`presets`** to avoid the cooking metaphor and, more importantly, to dodge the two collisions the obvious alternatives carried — "workspace" already means the `.quimby` project/state/durable-storage (a whole package, `resolveWorkspace`, `~/.quimby/workspaces/…`), "profile" is taken by `runtimeProfiles`/the `runtime-profile` package, and "template" by `@quimbyhq/template`. A legacy `recipes:` key still loads (folded into `presets`, presets winning a clash), so existing configs keep working. Separately, a top-level `default:` names the preset a bare `quimby up` (no preset) creates and a bare `quimby run` (no agent, no `--layout`) opens — and `quimby run --layout <name> --default` records it. The run-target model that shapes this: a preset is **not** parallel to an agent, it's parallel to a **layout** (agents/groups compose inline into a layout; a preset contributes its saved layout), so `run` opens either agents (composable positionals) or one named/inline layout — the positional stays unambiguously agents/groups, and a saved layout/preset is reached explicitly via `--layout`, with `default:` the only thing that makes the empty invocation meaningful. The default is persisted under the same rule as host bindings — auto-saved to ignored `.quimby/local.yaml` (or user config with `--global`), hand-settable in a tracked `quimby.yaml` for a team-shared default but never auto-written there.
- **A service is a dashboard-local command pane, not a retained session — so it stops on exit by construction**: a layout can place a named host command with a `$name` token (`services: { server: "quimby serve" }`, then `(host $server)`), giving a "cockpit" dashboard where one pane runs the server (or a log tail, `watch`, etc.) beside plain shells. The token grammar extends the existing host slot: bare `$`/`host` is an interactive shell, `$name` runs `services.name`. The lifecycle question — should the command survive a dashboard rebuild? — is answered by _where_ the pane lives: a service is a window in the **ephemeral view session** (exactly like a `host` shell), not a retained agent session, so when the dashboard is torn down (any exit, or the rebuild on the next `quimby run`) the pane dies and the command with it. This is deliberately the opposite of an agent (retained across dashboard rebuilds): an agent is durable work you reconnect to, a service is scaffolding around this viewing of it. It means a service like `quimby serve` **starts with the dashboard and stops when you leave** rather than leaking a background process — at the cost of restarting on each `run`, which is why `serve` should additionally be made idempotent (detect a live server and no-op) so an overlapping run never double-starts it. A retained-service model (a service that outlives the dashboard, link-windowed like an agent) was considered and rejected as the default: it reintroduces exactly the "who stops the server" bookkeeping the ephemeral pane avoids, and the stop-on-exit behavior is what the cockpit use-case actually wants.
- **A `@role` layout token is a role slot — it places a _type_, not named instances, and is an explicit sigil, not an implicit union**: a layout leaf can name a **role** with `@role` (`@review | @builder / @integration`), which expands at plan time to every instance of that role — agents whose `role` is that role, plus a legacy agent literally named it (mirroring `resolveAgentLaunchDefaults`'s `agent.role ?? agent.name` fallback) — tabbed into one pane, in **natural-sorted name order** (numeric-aware, so `builder10` follows `builder2`). Creation order was the first choice and was wrong on both counts that matter for a tab strip: it is _invisible_ (you cannot predict it without reading `state.yaml`) and it _drifts_ (a rename or rebuild re-inserts the key, silently reordering the pool). Sorting on the name makes the strip predictable from the names alone and stable across those operations; for the numbered pools this feature exists to serve, it is also simply the order the author wrote them in. This is the placement half of role-vs-instance: a role slot is a _region for a type_, so a `+1` of that role (notably a different-engine one — a Codex `builder` beside Claude `builder`s, via `quimby add --role builder --profile codex`) auto-appears as a new tab with no layout edit. Three deliberate choices. (1) **Explicit `@` sigil, not an implicit "bare name expands to its role"**: the union was considered and rejected because it is ambiguous under individual addressing — `builder | builder-2` (two panes, addressing instances) would silently expand pane 1 to _all_ builders and duplicate `builder-2`, action-at-a-distance that breaks the author's intent. `@` makes "the type" and "this instance" syntactically distinct, and it's consistent with the grammar's existing leaf-kind-by-sigil rule (`$name` = service, `$`/`host` = shell, bare = agent), so it's purely additive — no existing layout contains `@`, and agent names forbid it. (2) **A role slot is one tabbed pane**, not split panes: "builder on the right" is a region you switch instances within; wanting them as separate panes means addressing instances individually. Names are deduped _within_ a pane (`@builder builder` → one tab) but not _across_ panes (that's the author's explicit choice). A pane weight rides the slot (`@builder:70`): the parser's tab-member-weight check runs at parse time on the single `@builder` token, and expansion (after parse) legitimately yields a multi-instance pane with one weight. (3) **An empty role is a hard error**, not a silently-pruned slot (`no agent has role "builder" — create one with quimby add --role builder`), matching the existing `Agent "X" not found`. Mechanically it is one pure rewrite (`expandRoleSlots` / `expandRoleSlotNames`, in `@quimbyhq/layout`, driven by a `roleInstanceResolver` closure over state) run right after `parseLayout` and before validate/plan/tmux-mark — so those stages see only concrete names, and `quimby layout --json` (the VS Code viewport) receives already-resolved terminals, keeping quimby the single resolver. **The expansion must run on _every_ `run` path, not only the plan builder.** Originally only `buildResolvedLayoutPlan` (which backs `quimby layout --json`) expanded, while `quimby run`'s own dashboard paths (`runPanelDashboard`, `runNamedLayout`, and the flat bare-positional path) fed the raw layout straight to validation — so `@review` failed there as `Agent "@review" not found`, the JSON view and the actual launch disagreeing. The fix routes all of them through the shared expander: `runPanelDashboard` expands the parsed tree, and the flat/named paths expand their name lists via `expandRoleSlotNames` (so `quimby run @builder` opens that role's instances too), keeping the rendered dashboard and the published plan identical. **Empty-role is still a hard error** everywhere the expander runs. **Creation** (`up`/preset) does _not_ conjure an instance for a `@role` slot: it errors like any other unsatisfiable leaf unless the role is satisfied by a declared or live agent (see the layout-only-places decision below); **replica counts from a preset** (`@builder × 3`) remain a separate scaling feature — this decision is placement/rendering only.

- **A layout only _places_ agents; it never _creates_ them**: preset creation (`quimby up`, and `run`'s create-missing step) is driven by `presets.<name>.agents` **alone**. The layout is consulted only to _validate_ that every leaf it names is satisfiable — by a declared entry, a live workspace agent, or (for a `@role` slot) any instance of that role. An unsatisfiable leaf is a hard error that creates nothing, naming the leaf and pointing at declaring it under `agents:` / `quimby add` / dropping it from the layout. This reverses an earlier behavior where `resolvePresetAgentEntries` walked the layout and **conjured** any name it found missing (creating a same-named-role agent, or seeding one `<role>` agent for an empty `@role` slot). That was a real footgun the author hit: `quimby remove -f <agent>` plus deleting it from `agents:` but **forgetting the stale layout line** silently regenerated the agent on the next `quimby run` — resurrecting exactly the worker you were trying to shed while resource-starving the pool. Making the layout purely declarative-of-placement means removal sticks: the only way an agent comes back is to name it under `agents:` again. The empty-`@role`-slot-seeds-one convenience is dropped for the same reason — it created an agent from a _layout_ edit, the very coupling this removes; a preset that wants an instance declares one.
- **Runtimes validate before launch and tear down their sandbox on removal**: a `RuntimeAdapter`'s `setup`/`teardown` are no longer stubs. `setup` **validates the runtime CLI is installed** — `prepareLocalTmuxLaunch` calls it before any tmux work, so launching an `sbx`/`openshell` agent without the tool fails with a clear "not on your PATH — install it, or use `-r local`" instead of the agent's pane dying the instant it execs a missing binary. Only a missing binary (`ENOENT`) counts as absent; a quirky `--version` is assumed present rather than wrongly rejected. Validation is **local-only**: an SSH agent's runtime CLI lives on the remote host, so `prepareSshLaunch` skips the local probe (checking the wrong machine would be worse than not checking). `teardown` removes the agent's per-agent sandbox (named by the same UUID-keyed path hash as `run`) when `quimby remove` deletes a local agent — best-effort, swallowing failures so cleanup never blocks removal, and skipped for SSH (that sandbox is remote). The exact `sbx`/`openshell` removal verb is best-effort and may need adjusting as those CLIs settle.
- **Provisioning adopts-or-creates keyed on git origin; `restore` is the escape hatch, not the happy path**: the project UUID that namespaces the remote workspace (`~/.quimby/workspaces/<projectId>`) lives only in the ignored `.quimby/`, so losing that directory (fresh clone, `git clean -x`, new machine) used to force the user through `quimby restore` — a manual, alias-and-`--id` archaeology step — before they could run their configured workspace again. Worse, if they _didn't_ restore, the next `add`/`run`/`up` minted a **fresh** UUID and silently orphaned the old remote agents as unreachable garbage. Both problems have one root fix: make workspace resolution (`resolveWorkspace`/`ensureWorkspace`) **adopt-or-create** instead of create-blindly. Before minting a fresh id it (1) relinks local durable storage on a registry match, then (2) scans every **bound** host alias in config for a remote workspace whose git origin matches this repo — exactly one match is **adopted silently** (reusing its id + roster + remote clone), zero creates fresh, more than one throws for the user to pick (`restore --host <alias> --id <id>`). This makes remote provisioning **idempotent on git origin**, which is the anti-garbage guarantee: a duplicate workspace can no longer appear by accident. Three deliberate constraints keep the magic safe. **Bound aliases only** — silent adopt never prompts for an address (prompting mid-`run` is exactly the friction being removed); an unbound alias falls through to the existing explicit paths. **Unreachable is skipped, never fatal** — a dead VPN or sleeping host (or a probe past `QUIMBY_REMOTE_PROBE_TIMEOUT_MS`) degrades to "no match," so an offline command doesn't hang or crash; a purely-local project with no bound alias never touches the network at all. **`restore` stays** as the explicit, scriptable escape hatch for what auto-adopt won't guess (a different alias, cross-machine recovery, `--id` disambiguation) — it and the silent path now share **one** reconstruction core (`reconstructRemoteWorkspace` in `@quimbyhq/workspace`), so both produce byte-identical recovered state. This required `@quimbyhq/workspace` to gain a `@quimbyhq/transport` dependency (allowed by the DAG: workspace sits above transport), with the clack prompt kept in the CLI so the package stays prompt-free. The GC half is deliberately **adopt-only, never auto-delete**: since duplicates can't accrue going forward, cleaning up ones the old behavior already made is an explicit `quimby storage prune-remote --host <alias>` — it previews (or with `--force` removes) only the remote workspaces for _this_ repo that are _not_ the active id, never touching another repo's lanes or the workspace you are on, and refusing outright when there is no local workspace to identify the one to keep. A "prune on reconnect" default was rejected: deleting remote state during a routine `run` is exactly the surprise the boundary philosophy avoids.
- **SSH lazy init**: SSH agents are not set up remotely at `quimby add` time. The remote clone, tagging, and scaffolding happen on first `quimby run`. This allows adding SSH agents without an active SSH connection.
- **rsync as transport**: SSH agents sync the project source via rsync before each run. The remote clone is a local clone of the rsynced source tree — no direct git remote needed on the agent side.
- **User config/data roots follow the host platform, project state does not**: project-local control state stays at `.quimby/` because it is intentionally visible at the repo boundary. User-level config and durable workspace storage are different: they survive `git clean` and should feel native on the host. Linux defaults to XDG (`~/.config/quimby`, `~/.local/share/quimby`), macOS defaults to `~/Library/Application Support/quimby`, and Windows defaults to AppData (`Roaming` for config, `Local` for data). `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, and `QUIMBY_DATA_HOME` still override those defaults so power users can pin storage explicitly.
- **tmux is the universal substrate; the dashboard is a viewport**: every agent — local or SSH — always runs in its own persistent tmux session (no foreground path). Disconnecting doesn't kill the agent. `quimby run <agent>` does `tmux new-session -A` against the stable-ID session name, so it **grabs the one canonical session wherever it is launched** (started here, by `start`, or shown in a dashboard) and creates it only if absent; the window label is refreshed to the display name on every (re)attach so it tracks renames. Running several agents (`quimby run <a> <b>`) opens a **dashboard** — a stateless viewport session that `link-window`s each local agent's own window in as a tab (SSH tabs ssh-attach the remote session; `host` is a plain shell). link-window (not nested `attach`) is deliberate: the agent's window is _shared_, so the dashboard tab and a direct `quimby run <agent>` are two live views of the same window, yet only the dashboard's single status bar shows — no nested inner status bars, and nothing set at the dashboard's session scope alters the agent's own session. Because the dashboard only borrows a view, the per-agent sessions outlive it, so it is torn down and rebuilt on each run (dodging tmux's "duplicate session"), tabs are numbered from 0 to match `Ctrl-b 0/1`, and per-tab activity/silence highlighting is set as window options — shared with the linked agent session but invisible there, since that session's plain `window-status-format` doesn't react and visual-* stay off.
- **No raw-SSH fallback for retained agents**: SSH agents still require remote tmux even when their repo already exists. A raw `ssh <host> <entrypoint>` fallback would appear to work but would lose the properties users rely on: reconnectable sessions, `start`/`stop`, `nudge`, dashboards, and stable session names. So `prepareSshLaunch` checks remote `tmux` on every launch and fails before constructing the session if it is missing; first-run provisioning still checks `git`, `rsync`, and `tmux` together.
- **Quimby owns its tmux, on a dedicated server**: rather than depend on whether the user has a good `~/.tmux.conf`, Quimby runs all its tmux on an **isolated server socket** (`tmux -L quimby`) started from a **bundled config** (`-f .quimby/tmux.conf`, generated by `renderTmuxConfig`; the remote twin is written over transport). The isolation is the point: Quimby's settings never leak into the user's default server, and its sessions never clutter the user's `tmux ls`. The config is **layered** — calm aesthetic defaults (a muted status bar showing the agent/window name, instead of tmux's default bright-green bar) → `source-file -q ~/.tmux.conf` so the user's own keybindings/theme still apply → Quimby's functional must-haves set _last_ so they win: true-color passthrough (`terminal-overrides ",*:Tc"`), `mouse on` (scroll wheel reaches scrollback — default tmux needs copy-mode), a generous `history-limit`, and stable window names. This fixes what session-scoped options couldn't: true-color (needs `default-terminal`/overrides at server start) and scrollback depth (needs `history-limit` before the pane is created). Every quimby tmux call — `new-session`, `has-session`, `send-keys` (nudge) — targets `-L quimby`, so they all see the same sessions. One of those must-haves is **`window-size largest`**, which exists because the dashboard _shares_ an agent's window rather than copying it: the agent's own session and every dashboard showing it are separate clients on one window, so under tmux's default (`window-size latest`) the window follows whichever client was used last. A leftover `quimby run <agent>` terminal is enough to drag the agent down to its width — the TUI reflows to 90 columns and stays there while the dashboard pane is twice that, which reads as "the pane resized but the app didn't". `largest` makes the biggest viewer win. The trade is deliberate and asymmetric: a small client then sees a clipped view of a larger window, which is recoverable by looking elsewhere, whereas a TUI reflowed to the wrong width is not — it has already thrown away the layout. Verified on tmux 3.6: with `latest`, attaching a 90x24 client to a 200-column agent collapsed its window to 90x23 (and the process's `stty size` with it); with `largest` it held at 200x48. Note this is the one layer quimby controls — tmux itself propagates SIGWINCH correctly through the whole wrapper → view → linked-window nesting, so a process that still refuses to reflow is the app or its sandbox pty, not the courier. A companion binding (`prefix + =`) **re-fits** a window whose app is drawing at a stale size. This is a distinct failure from the sizing one: tmux can have the window right while the app never re-laid-out, because a TUI reflows on SIGWINCH and nothing redelivers one after the fact. So the binding nudges the width by a column and back, which is two genuine SIGWINCHes. The non-obvious half is the second step: `resize-window` silently pins the window to `window-size manual`, so a naive jiggle "fixes" the app and leaves the window permanently ignoring its clients — strictly worse than the stale size. Unsetting the window-local option restores tracking _and_ delivers the second resize. The two steps also need a beat between them: chained on one line they coalesce, leaving the pty a column narrower than the window (verified on tmux 3.6), so the binding backgrounds a short shell rather than chaining tmux commands. Other trade-offs: `-f` is read only at server start, so config changes apply after the quimby server is next empty and restarts; and with mouse mode on, click-drag selects into tmux's copy buffer (hold Shift for the terminal's native selection). To reach a session by hand, use `tmux -L quimby attach` (but `quimby run` handles attach for you).
- **Nudge: wake a live agent in place, policy per movement**: writing `assignment.md` or dropping a parcel in an inbox is silent — a running interactive agent won't notice until its next prompt, leaving the user to switch terminals and type by hand. So quimby can inject `<text>` + Return into the agent's tmux session (`tmux send-keys`, keyed by the agent's stable UUID, so a rename never loses it). The default policy follows how directed the movement is: **assign** always nudges (you named one agent and gave it a task), **dispatch** nudges by default (the boss agent authored an addressed note with intent), **handoff** nudges only when the parcel carries a **note** — the instruction half — since a handoff is often pure data (a diff with no note); `--nudge`/`--no-nudge` force either way. The standalone **`quimby nudge <agent>`** is the explicit, ad-hoc live channel: with no `-m` it types `"continue"` (the lightest kick). **`-m` is an ergonomic alias for `assign`** — it persists the message as the agent's assignment, runs the normal sync, then wakes it — because a task typed into a session is lost on the next context reset, and "I told the agent" should survive that. **`--raw -m` types verbatim**, for genuinely ephemeral input and CLI control commands like `/clear` or `/model …`. The wake is only the wake; the durable work lives in `assignment.md`/the inbox, so a missed or skipped nudge only delays, never loses. A local non-tmux agent runs in the foreground (the user is already attached), so there is nothing to wake. There is deliberately **no separate `send` verb**: a first-class "send the agent instructions" command would compete with `assign` for the task-giving slot and tempt users onto an ephemeral channel when they need a durable task; folding arbitrary/control sends into `nudge -m` keeps the capability without advertising a verb that cannibalizes `assign`. Durable task-of-record is `assign`'s job; `nudge` is the live, ephemeral poke. **`nudge --all`** broadcasts (e.g. `--all --raw -m "/clear"`, since a durable assignment cannot be broadcast) but first **probes tmux for live sessions** (`has-session`) and targets only those — so it never spams dead agents, and the logged target list shows exactly which live sessions received it.
- **`directs` makes the authority graph govern interruption, not just delegation — active vs passive channels**: a declared `directs: [<agent|@role>]` edge (in tracked `quimby.yaml`, copied onto agent state at creation) is read two ways at once. As **authority** it host-stamps an agent-authored parcel `userDirected` when it travels the edge (the standing-relationship generalization of `delegate`'s per-message user grant). As **interruption** it decides the nudge: an agent-authored parcel wakes its recipient **only** when it is directed (a `directs` edge or `delegate`), an **escalation** (a bounded upward summon, honored only to a permitted target — every agent that `directs` the sender, or an explicit `escalatesTo` allow-list — else normalized to an ordinary advisory), or a **reply** (answering a question); every other parcel — an ordinary advisory handoff, the status mirror — is **passive**, landing in the inbox to read on the recipient's own turn. This moves dispatch's nudge trigger from "has a note" to "is directed," the fix for the token/clobbering pain: routine agent chatter no longer wakes anyone, only genuinely directed/escalated/answered work does. It all rides the **one handoff parcel** (tags on `meta.yaml`: `userDirected`/`escalation`/`expectsReply`/`replyTo`), never a new channel — status is the sole non-parcel mirror. Paired with **§7** (never inject the session you are **working in** — automated nudges defer, the explicit `quimby nudge` forces) and a per-poll-cycle **coalesce** (N directed parcels for one recipient → one wake). The agent-side verbs `escalate`/`ask`/`reply` are sugar over `handoff` writing the intent tags; the human `quimby handoff` stays note-nudged (the human is the authority). Rejected: a per-verb permission matrix or a handoff allow-list (speculative surface — `directs` default-deny **is** the whitelist as data); message text granting authority (only the host-established edge does). **The graph is editable because `sync` re-reads it.** `directs` is still _stored_ on agent state (dispatch resolves the edge from state alone, so a carry never depends on config being loadable), but it is **re-resolved from config on every `quimby sync`** rather than only at creation — the same non-destructive path that already refreshes the scaffold, and for the same reason: a config edit must reach in-flight agents without a rebuild or a session kill. Config wins when it declares the agent — a preset entry, or `directs`/`escalatesTo` on its **role** (which also covers replicas and a bare `quimby add --role`) — and a **removed** edge clears the stored one, so revoking authority works, not just granting it. An agent no config names keeps its stored edges, so a hand-set edge is never silently wiped. Refreshing at _sync_ rather than at _dispatch_ was chosen deliberately: dispatch is the hot path (the server runs it every poll cycle) and must stay a pure state read, while `sync` is the one verb whose whole job is "bring agents up to date" — so `quimby sync --all` after a graph edit, and the next dispatch obeys it. **Known limitation (shipped v1):** the reply interrupt is _trust-based_ at the tag level — a `replyTo` wakes the asker once the host confirms the named parcel is really in the replier's inbox, but it does not yet verify that parcel carried an outstanding `expectsReply`. See coordination-proposals §6.
- **Delivery is durable, the wake is not — so an unattended fleet re-announces, retries, and releases**: running overnight with nobody watching turns every silent skip into "the fleet stalled until morning", which is strictly worse than a duplicate nudge landing under an idle cursor. Three places quietly assumed a human would notice, and each is now biased toward waking. (1) **A failed carry retries.** The attempt-once rule existed so a bad address can't loop, but it keyed on the parcel _version_, so a transient failure (unreachable host, fs hiccup) stranded an unchanged draft forever. Now a `failed` carry forgets its attempt and retries next cycle, while a **bounce** (`unknown` recipient) stays attempt-once — retrying a typo can never succeed. (2) **An idle focused pane stops holding.** §7's focus rule reads "is this the window the human is typing in", but a window left open overnight _is_ focused by that test, so the one agent you most need woken would be held until morning. A client with no input for three minutes no longer counts as focus. (3) **Unread inboxes are re-announced.** A nudge can be lost to a dead session, a failed `send-keys`, or a coalesce that fired mid-restart; the parcel is on disk but nothing says so. A poll-cycle sweep re-pokes idle agents sitting on unread parcels — bounded by an interval, capped at three reminders for an unchanged inbox (after which it reports the agent as stuck rather than poking all night), and never aimed at an attached session (a human is there) or a stopped one (no prompt to type into). The bounds matter as much as the sweep: an unbounded reminder loop against a wedged agent is how a safety net becomes the outage. What is deliberately _not_ automated: restarting a dead agent, and supervising `quimby serve` itself — both are real overnight failure modes, but recovering a crashed process is a different concern from courier delivery, and guessing at it silently would be worse than reporting it.

- **The reminder sweep announces nothing on first sighting — a net catches what the primary path dropped, after it has had its chance**: the sweep re-announces unread parcels, and it announced a parcel the moment it saw one. But the sweep shares no tracker with whoever _carried_ that parcel, so "nobody woke this agent" and "someone just woke this agent" look identical to it, and it woke the agent a second time for the same parcel. Three carriers hit it. (1) **The wake bundler.** Delivery is immediate but the wake waits out its 12s window, so for two or three poll cycles the parcel sits unprocessed with nothing yet sent — the sweep announced it seconds _before_ the bundle flushed the real wake. Observed as `parcel <p> unprocessed in your inbox` followed by `delegated task <p> from <sender>`, in that order, for one parcel. (2) **Any CLI carrier** — `quimby delegate`/`handoff`/`dispatch` runs in a different process, nudges, and the server's next poll cycle re-announced the same parcel ~5s later. (3) **Advisory parcels**, which is the worst of the three: §6a delivers them deliberately _without_ a wake, and the sweep announced them anyway on the next cycle — quietly undoing `nudge: directed` for any agent whose tray was otherwise clear. One rule closes all three: a first sighting is **recorded, never announced**, so the carrier's own nudge rule governs a fresh parcel and the sweep only speaks for what is still unprocessed an interval later. Two smaller fixes ride along in their own layers: `autoDispatchOutboxes` now reports recipients whose wake is still _pending_ (not only ones it flushed), since a pending wake is not a lost wake; and the same is recorded through the existing `noteInboxDelivery`, rather than a second mechanism beside it. The cost is that a genuinely lost wake is caught one interval later instead of one poll cycle later — the same bound every repeat already lives under, and the right trade against re-waking an agent for work it was just told about. The general rule: **a safety net must not fire on the same event as the mechanism it backs up**, and when it cannot observe that mechanism, waiting is how it tells them apart.

- **`nudge` names which parcels wake an agent, and it is the RECIPIENT's setting**: the key is `all` | `directed` (default) | `never`, settable per agent, per role, or workspace-wide. This is its third spelling, and the churn is the instructive part: it began as `overAttached` (a boolean about a _hold_, where `false` confusingly meant _more_ holding), became `always|focus|never` (about whether _injection_ was permitted), and only then landed on the gate people actually mean. The tell was a user reaching for `nudge: always` **twice**, expecting "wake me for everything", and getting neither a wake nor an explanation — because that value governed only the hold, while the _interrupts_ gate upstream had already classified the parcel as advisory and skipped the nudge entirely. Two orthogonal knobs behind one word is a trap, so the policy now owns the gate that decides interruption, and the focus guard stops being a policy value at all. **`all` is the load-bearing addition**: an unattended overnight fleet needs every parcel to wake its recipient, which no combination of the old values could express — the human is asleep, so "only directed work interrupts" just means the fleet stalls until morning. It resolves **recipient-first** (its own `nudge`, else its role's, else the workspace default) because an interrupt setting answers "how much may I be interrupted?", a property of the agent whose context gets spent; a _sender_-side setting was rejected as the same category error as letting message text grant authority. Stored on `AgentState` and refreshed by `quimby sync` alongside the coordination edges, so a config edit reaches a live agent without a rebuild; `always`/`focus` are accepted as legacy spellings. Human-initiated verbs (`assign`, `handoff`, `delegate`) keep their own nudge rules — naming one agent on the command line _is_ the decision to interrupt it, and a config key that silently swallowed a task you just assigned would be worse than any interruption.

- **`whenFocused` is the second gate, and it had to become configurable because the first one kept getting blamed for it**: §7 holds a nudge aimed at the pane you are typing in, and that hold was hardcoded — no config value, on the reasoning that "don't type over live keystrokes" is never something a fleet wants disabled. That reasoning is right about the _default_ and wrong about the _absolute_, and the evidence was already in this log before the feature existed: the `nudge` entry above records a user reaching for `nudge: always` **twice**, expecting "wake me for everything", and getting neither a wake nor an explanation. It happened a third time, and the third time named the case the original reasoning missed — a fleet you **watch but do not converse with**. There, holding is not protection, it is silence: nobody is typing anything worth protecting, the pane just happens to be the focused one, and a wake that waits for you to look away is a wake that never comes. The 3-minute idle release covers stepping away; it does not cover sitting there reading. So the guard keeps `hold` as its default and gains `whenFocused: hold | nudge`, resolved recipient-first (agent → role → workspace → `hold`) and refreshed by `quimby sync`, exactly like `nudge` and the coordination edges. **The two stay separate keys**, which is the whole point: `nudge` answers "which parcels are worth waking this agent for", `whenFocused` answers "is typing into it acceptable right now". A parcel must pass the first to reach the second, and that ordering is precisely why `nudge: all` looked broken — it _worked_, and then the gate nobody could see or configure held the keystroke. Folding the guard into `nudge: all` was the tempting fix and was rejected: it would make "wake me for every parcel, but not mid-keystroke" inexpressible, and it re-creates the two-knobs-behind-one-word trap that the `overAttached` → `always|focus|never` → `all|directed|never` churn was all about — just pointing the other way. Two supporting fixes ship with it, because the mechanism was never the only problem: the held-nudge line now **names `whenFocused`** (it previously offered only `quimby nudge <agent>`, so the hold was a dead end you had to read the source to escape), and `quimby serve` **reports both policies at startup**, since "delivered, nobody woken" is otherwise indistinguishable from a broken courier. The generalizable lesson is the one the `nudge` entry already half-learned: a gate the operator cannot see, name, or configure will be attributed to whatever gate they _can_ see — so every silent stand-down has to say its own name.

- **The focus guard's default is derived from the authority graph, and holding means _typing_ rather than _looking_**: `whenFocused` shipped as `hold`-by-default with an explicit `nudge` opt-out, which was right in shape and wrong in ergonomics — an 8-agent fleet needed seven per-agent overrides to express "wake everything except the one I talk to", and the blunt `nudge` value bought that by disabling keystroke protection outright. Two fixes, and the second is the more fundamental. **(1) `directed` is the new default**: an agent something `directs` is machine-driven, so a nudge types into it even while you watch; an agent nobody directs is the one you converse with, so it holds. That is the same inverse-of-`directs` derivation escalation already uses, it needs no new state (`directorsOf` existed), and on a `principal → manager → workers` chain it yields exactly "all but the principal" from a graph the user already declared — including for workers added later, which a per-agent list would silently miss. **(2) The guard now distinguishes watching from typing**, which is what the request was actually about ("I want to view what's going on without being afraid I'm interrupting"). The signal was already there and was being thrown away: tmux's `client_activity` is the time of last _input_, not of attachment or redraw — verified on 3.6, where an attached idle client holds a frozen value and one keystroke bumps it — but the code compared it against a hardcoded **180s**. So supervising an agent (type a correction, watch it work) held its nudges for three minutes after every keystroke, and forever if you interjected periodically; merely _looking_ at a fleet slowed it down. The default is now 45s and configurable as `focusGrace`. The asymmetry sets the direction of caution: too long silently stalls a fleet, too short lets a nudge append to a half-typed prompt and submit it — recoverable versus corrupting — so the value falls back rather than shrinking on a bad parse, and the docs say to raise it if you compose slowly. Together they give the property neither gave alone: on a worker you are watching nothing holds, and on the agent you talk to holding tracks your actual keystrokes instead of a three-minute shadow. Rejected: keeping `hold` as the default and documenting the overrides (it scales with fleet size, and the config it demands is exactly the graph already declared); making `nudge` the default (blanket-disables protection on the one agent that needs it); and inferring "watching" from window activity rather than client input (a busy agent looks identical to a watched one — the same trap §7 already rejected for `session_activity`).

- **The focus guard matches a local agent by window id and an SSH agent by project-scoped name — a bare window name is not an identity**: §7's hold fired for agents the user was not typing in, in a window they had not touched. The cause is that the guard read a machine-wide fact as if it were project-local. Every workspace shares one tmux server (`tmux -L quimby`), and `getFocusedTmuxWindows` runs `list-clients` + `list-panes -a` across the whole socket — so `focused.names` mixes every project on the machine. The guard then asked `focused.names.has(displayName)`. Agent names repeat across projects by design (`review`, `builder` are the obvious names, and the shipped preset uses exactly those), and a window NAME carries no project id — only the _session_ name does (`qb-dash-<projectId>`, `qbv-<projectId>-<n>`; an agent's own session is keyed by agent UUID). So typing in one workspace's `builder` pane held a different workspace's `builder`, and the only visible trace was a 2-second status-line flash in a window nobody had touched. The fix splits the two cases by what is actually identifying. A **local** agent is matched by `window_id`, which is unique on the server and stable across `link-window` (so it matches from the agent's own session or a dashboard tab) — the name check was pure ambiguity there and is gone. An **SSH** agent genuinely cannot be matched by id (its window lives on another tmux server, where ids are meaningless), so it keeps the name match but scoped to sessions belonging to _this_ project; with no project id known, it claims nothing rather than guessing. This is the same lesson as the `session_attached` inversion §7 already learned, one level down: an identifier that is not unique in the space you are querying will silently match a stranger, and the more workspaces the user runs, the more often it does. Rejected: comparing names plus a project prefix on the _window_ name (window names are user-facing labels and renaming one would break the guard); and dropping name matching entirely (it is the only signal an SSH agent has).

- **An agent session is created at the operator's terminal size, because the pty it is born with may be the only one it ever has**: `tmux new-session -d` with no `-x/-y` creates the session at tmux's default **80x24**, and that is the size the agent's pty — and anything the runtime layers underneath it — starts at. Linking that window into a wide dashboard resizes the tmux _window_ afterwards, which is enough for a plain shell (verified: `stty size` follows through the whole wrapper → view → linked-window nesting). It is _not_ enough when a sandbox runtime allocates the container's pty at creation and never forwards the later SIGWINCH: the app then renders at 80x24 for the life of the process, and nothing above it can help — not resizing the pane, not `Alt+z` zoom, not detaching and reattaching, not `quimby run` again, and **not even `quimby restart`**, which created another sizeless 80x24 session. That last one is what made it look unfixable rather than merely wrong. The wrapper dashboard session already passed a size; agent sessions never did, which is exactly backwards — the wrapper is a viewport that resizes freely, while the agent session is the one whose birth size may be permanent. Quimby now measures the launching terminal and passes `-x/-y` on every agent `new-session`, omitting it when there is no TTY. This is deliberately only the half quimby owns: forwarding a _later_ resize into a sandbox is the runtime's job, and if it never does, being born right is the whole game.

- **§7 holds the nudge for the pane you're _working in_, not every session a client touches**: the rule exists so an automated nudge never types over a human mid-keystroke, and it first spelled that as "is a client attached to the agent's session?". That premise silently inverts under a dashboard. A quimby layout attaches a client **per pane** — and for an **SSH** agent the tab is a real `ssh … tmux new-session -A` onto the agent's own remote session, so `#{session_attached}` reads 1 for _every_ SSH agent in the layout the moment it opens. The result was the exact failure §7 was meant to be a narrow exception to: a fleet where every agent is permanently "attached" and therefore **never nudged** — the user back to hand-carrying parcels, with the held-nudge line the only clue. (A _local_ agent dodged it by accident: dashboards reach those by `link-window`, which shares the window without attaching a client, so they read `running` and kept working. Verified on tmux 3.6: link-window leaves the source session at `attached=0` while the viewport session reads 1.) The fix is to ask the question §7 actually means — **is this the window the human is typing in?** — resolved by walking the focus _chain_: from each real (non-nested) client, follow its session's active window → active pane → the nested client that pane hosts (a panel dashboard nests wrapper → view → agent), until it reaches a pane hosting no client. Only those endpoint windows are focused. Matching is by `window_id` (stable across `link-window`, so a local agent's shared window matches from either side) and by window **name** (an SSH agent's window lives on a different tmux server, where ids are meaningless, and its dashboard window is created with the agent's name). One conservative fallback preserves the original guarantee where no local focus information exists: an SSH agent whose remote session is attached with **no** local quimby window carrying its name is a bare `quimby run <agent>` in a plain terminal, so it holds. The single-agent `quimby run` case is unchanged — you are the focus endpoint, so it still holds. A held nudge also **flashes the status line of the session it was held for** (`display-message`), because the hold was otherwise invisible to the one person it is held _for_: they are working in that pane while the only notice goes to the server log elsewhere. Injecting the courier text into the pane _without_ Return was considered as the alternative and rejected — it is not a gentler nudge, it is the same intrusion with a worse failure mode: `send-keys -l` inserts at the cursor, so a half-typed prompt becomes `please refactor thquimby · parcel …e auth module` and gets sent as that. The current rule fails visibly and recoverably ("the nudge waited"); injection fails silently ("your prompt was corrupted"). It is also unknowable whether a TUI is idle at an empty prompt — these are not line editors, and a character arriving at a `y/n` permission prompt is consumed as the answer. The status line reaches the human without ever touching stdin, which is the property that matters. The guard's _default_ is deliberately always-on, because "don't type over live keystrokes" is the right default for a pane you converse with, and `quimby nudge` forces past it for one message. It was originally **not** configurable at all — see the `whenFocused` entry below for why that absolute did not survive contact with a fleet you watch rather than talk to. How much work interrupts you remains the separate `nudge` policy. Rejected: making the config key the whole fix (it trades clobbering for silence — the user must choose between being interrupted mid-keystroke and not being told at all, when the machine can simply know which pane is focused); and inferring focus from `session_activity` timestamps (a _busy_ agent looks identical to a _watched_ one).

- **A held nudge is deferred, not dropped — and a hold is not an announcement**: §7 holds a nudge aimed at the pane you are typing in, and the work stays durable in the inbox, so the design called the hold harmless. It was not, because nothing retried it promptly and the accounting miscounted it. The only retry path was the reminder sweep, which re-announces an unread inbox every 10 minutes and gives up after 3 — and it recorded the attempt **before** nudging, so a held attempt counted exactly like a delivered one. Sitting in an agent's pane for twenty minutes therefore spent all three reminders without a single one reaching it, after which the sweep stopped and reported _"has ignored N parcel(s)… may be stuck or out of context"_ about an agent quimby had never actually told anything. The fix is one reordering plus one distinction: attempt first, record only on a real send, and let `nudgeAgentSession` report which it was (`sent` / `held` / `skipped` / `no-session`) instead of returning void. A held entry keeps its previous count and is exempted from the interval, so the existing sweep retries it on the **next poll cycle** — which, combined with `focusGrace`, means the wake lands about one cycle after you stop typing rather than up to ten minutes later or never. No new tracker and no new mechanism: correcting the accounting _is_ the retry. Two details earn their place. The hold is narrated **once** per unread inbox, not once per retry (`quietHold`), or a watched pane would re-flash and the server log would repeat every few seconds for as long as someone types. And `no-session`/`skipped` are treated like `held` rather than like `sent`, because none of them reached the agent — the cap exists to stop poking an agent that is _ignoring_ work, and an attempt that never arrived is not evidence of that. The generalizable rule: **a retry budget must count deliveries, not attempts**, or the thing preventing delivery silently spends it.

- **A conflict nudge is forced and offered, never silently held**: when a `sync`/`merge` rebase conflict routes resolution back to the agent, the courier request that _tells it what to do_ ("rebase onto `<ref>` and resolve conflicts") is the entire value of the interaction — so it bypasses the §7 hold entirely. This was a real regression: once §7 landed, that message was swallowed by "Held nudge for …" for any attached agent, leaving the user with a failed sync, an unresolved agent, and no idea what to say to it. The rule that falls out is a clean line through every nudge site: a nudge that is the **direct product of a command you just ran** is human-initiated (force it), while a **background** courier (auto-dispatch, the poller, `assign`'s side-effect nudge) respects the `nudge` policy. On top of that it is _offered_ rather than assumed — interactive runs confirm (`y/N`, default yes) and print the paste-able `quimby nudge` when declined, so the user can choose to fix it themselves or not interrupt a working agent. The two verbs differ only in their non-interactive fallback, each preserving its own prior contract: `merge` fires (it has always auto-nudged, and a script that merges expects the agent to be told), `sync` only prints (waking an agent onto a broken baseline is the user's call — the same principle as `assign` suppressing its nudge after a failed pre-sync, and as the wedged-repo error offering a ready-to-paste command rather than firing one). Rejected: auto-firing from `sync` unconditionally (it contradicts the offered-never-auto-fired rule the wedged case already established); and leaving the message subject to the policy (a `nudge: never` fleet would then have no way to be told about a conflict at all).
- **Everything config declares about an agent is refreshed by `sync`, because snapshot-at-creation fails silently every time**: `role`, `directs`, `escalatesTo`, `nudge`, and the charter are all written onto agent state when the agent is created — and each one, left un-refreshed, produced the same class of bug: config says one thing, state says another, and the divergence is invisible until something quietly does less than you asked. `role` was the worst of them, because it fails in two directions at once — a stale role drops the agent out of its `@role` layout slot (a pane that should hold four builders holds two, with no error, since the slot is satisfied by the ones that did match) _and_ resolves its launch config through the wrong profile. It was reported exactly that way: "builder and builder4 appeared, builder2 and builder3 didn't." So `sync` now re-resolves the role from config alongside the rest, with one asymmetry: an absent config role never _clears_ a stored one, because `quimby set <agent> --role` remains the way to attach a role to an agent no preset declares. The general rule this settles: **config is the source of truth for what an agent is, state is the cache, and `sync` is the one verb that reconciles them.** Anything added to a role or agent entry from here on must be refreshed there too, or it inherits this bug by default.

- **A silent prune is a bug report waiting to happen**: the layout planner drops disabled agents so you can `quimby disable` one without editing the `expr` — deliberate, and it printed nothing, which made an intentional omission indistinguishable from the stale-role omission above. `run` now names the agents a layout skipped and how to bring them back. The pattern across this whole area is the same: every place the courier does less than the config appears to ask — a held nudge, an advisory delivery, a refused escalation, a pruned layout leaf, an ignored config key — has to say so, or the operator's only recourse is to guess.

- **A role's charter belongs in config, not in `assignment.md`**: the two look interchangeable and are not. `assignment.md` is the _current task_ — `quimby assign` overwrites it, and the agent is instructed to keep it true as the user retasks — so standing role behaviour written there ("batch your inbox and escalate once with a synthesis", "never re-task a builder directly") is destroyed by the next assign, silently, exactly when the fleet is busiest. The charter is the other half: who the agent _is_ across every task it will ever be given. It lives as `instructions` on a role (or on an agent entry, which replaces its role's) and renders into the generated `CLAUDE.md`/`AGENTS.md` as a `## Your role` section, riding the same scaffold refresh as the coordination edges — so it is version-controlled, reviewable in a diff, applied to every instance of a role at once, and reaches live agents on `quimby sync` without a rebuild. The split mirrors the one already drawn between the Quimby tier (generated, regenerated) and `assignment.md`/`status.md` (the agent's own, never touched by a refresh). Rejected: expressing it as a long `quimby assign` per agent (lost on retask, per-instance, invisible to review), and a separate charter _file_ the user maintains per agent (a second place to edit that config already describes).

- **The conflict lead names `origin/<ref>`, and the agent is told not to fetch — a bare branch name is a silent no-op and `origin` is unreachable from a sandbox**: the `rebase onto <ref>` courier interpolated the agent's `syncRef` verbatim, so it read `rebase onto main`. But an agent's clone has its own local `main`, and `git rebase main` while sitting on `main` reports "up to date" and replays nothing — the agent then believes it resolved a conflict it never touched, and the same overlap surfaces again on the next merge. Naming `origin/main` is unambiguous and is the ref Quimby actually advanced. Separately, the generated instructions opened with `git fetch origin`, which **cannot work**: an agent's `origin` is a host filesystem path, not a URL, and inside the sandbox that path resolves to the agent's own mounted tree rather than a repository — the fetch dies with `does not appear to be a git repository` (verified from inside a live agent). Agents dutifully tried it, hit the wall, and improvised. No fetch is needed at all: `syncAgent` fetches on the host, where the path _is_ a repo, before the rebase it attempts on the agent's behalf — so by the time the conflict lead is sent, `origin/<ref>` is already at the tip. The rule both halves share: **an instruction handed across the boundary must be executable on the far side of it**, and a ref name that happens to also name something local is not a ref name.

- **The agent is told its own place in the graph, by name — an unnamed edge is an unusable one**: the coordination edges live in host state the agent cannot read, so its context could only ever say "escalate to your director" in the abstract. That made the interrupt channel quietly unreliable: the agent had to _guess_ a recipient, and a guess that misses a permitted target is **silently normalized to an ordinary advisory** — no error, nobody woken, and the human back to relaying, which is the exact failure the `directs` work exists to remove. So the resolved graph (concrete names, `@role` slots already expanded) is rendered into the agent's `CLAUDE.md`/`AGENTS.md` through a `{{coordination}}` clause: who it directs, who it may escalate to, and — when it has neither — an explicit "everything you send is advisory" so the absence reads as designed rather than broken. It rides the existing scaffold refresh, so it is rewritten on every launch **and** every `quimby sync`, exactly like the rest of the Quimby tier: a graph edit reaches a live agent without a rebuild, ingested at its next context reset. The names are resolved by the caller (which holds the state) rather than by the template, keeping `@quimbyhq/template` a pure renderer with no state dependency.

- **The reply window outlives the GC — `sync` sweeps processed parcels but keeps their names**: the reply-interrupt is authorized by _correlation_ ("is the parcel you're answering really one you received?"), which read the `in/received` and `in/processed` trays. But `quimby sync` prunes `in/processed` on every run, so an agent that marked a question done and then answered it after any sync had its reply **silently downgraded to an advisory** — delivered, nobody woken. The two features were each correct alone and destructive together, and the failure was invisible from both ends: the replier saw a successful publish, the asker saw nothing at all. The fix keeps the GC (processed parcels carry diffs and are genuine cache) and makes it record what it removes: a names-only `in/processed.ledger`, a few bytes per parcel, which the correlation check consults as a third source. Paired with an agent-side guard, since the host's answer arrives too late to help: `agent.sh reply --to` now verifies the name against its own inbox (received, processed, or ledger) and **refuses**, listing what it actually holds, rather than publishing a parcel destined to be downgraded. Together they close both halves — a wrong name fails loudly at the source, and a right name keeps working after a sweep. Rejected: not pruning `in/processed` (unbounded diffs), and tracking outstanding questions in state (a second source of truth for something the mailbox already knows).

- **A renamed repository must not become an adopted one: identity is refreshed, corroborated, and never silently taken**: workspace adoption keys on two identifiers — the registry's `repoRoot` path and the workspace's `sourceRepo` origin — and a single rename staled both at once. Reported in the field: a project renamed `flight-oracles` → `flight-fixtures`, a new `flight-oracles` created in its place, and the new project inherited the old one's workspace — same durable storage, same UUID, therefore the same remote workspace and the same two agents, whose UUIDs appeared verbatim under the new checkout. Four failures compounded, and each is fixed where it lives. (1) **`sourceRepo` was written once at creation and never revisited**, so the renamed project kept identifying as a repo it no longer pointed at, and that stale value is what the registry stores and matching reads; it is now refreshed from the git origin on every resolve. The remote-less case is refreshed too but differently — there `sourceRepo` falls back to the repo path, so the path _is_ the identity and a moved checkout must re-point it, while a stored URL is never replaced by a path, because losing a remote does not make a project a different one. (2) **A registry `repoRoot` match won outright**, never consulting the origin — pinned, as it happens, by a test asserting exactly that. The precedence is right when the two agree or one is unknown, and wrong only when they _disagree_, which is precisely the recycled-path signature: rename a checkout and the vacated path is free for a different project to occupy. So a path match now requires that the origin not contradict it. (3) **Adoption could overwrite the workspace it adopted from.** Reconstruction ends in `ensureDurableWorkspace` + `saveState`, which symlinks this repo's `.quimby` at the adopted id's storage and writes `state.yaml` **through** that link — so adopting a workspace another checkout owns replaces that checkout's state with one rebuilt from this repo's branch and config. That is data loss, not a collision, and it is now refused when the registry maps the id to a different `repoRoot` that still exists. The liveness qualifier is load-bearing in both directions: a claim whose directory is gone is the moved-or-deleted checkout `restore` exists to recover, and blocking there would break the recovery this path is for. (4) **A real `.quimby/` meeting existing storage for the same id hit a bare `return`** — the project then ran unlinked on the local directory while the storage it believed it owned sat elsewhere, two `state.yaml` files for one id with no notice. Empty storage is an interrupted migration and is completed; two populated directories are reported, because which is authoritative is not something quimby can know. The through-line is the one this codebase keeps relearning one layer at a time: **an identifier nothing revalidates will eventually name something else**, and the moment two of them disagree is information, not noise. Rejected: healing the registry by path alone (it is the identifier that went stale); making adoption prompt (it runs inside an ordinary `add`/`run`, and the design's whole point is that reconnection is silent when unambiguous — so the fix is to make ambiguity detectable, not to ask on every launch).

- **Base staleness was visible in one direction only, and the missing one rides the mirror that already exists**: `agent.sh` tells an agent when `quimby/base` is ahead of _it_. Nothing told it that a **peer** is ahead of the base — that a peer holds work living only in that peer's clone. The asymmetry is expensive in a way the reported direction is not: two agents independently fixed the same defect and the second could not land, a P0 was filed with airtight proof against code a peer had repaired hours earlier, and a reviewer could not read the source it was reviewing. The instinct is to call this a missing channel, but the channel was already there and merely empty — status mirrors are the ambient pull-on-demand lane, and `formatStatusSnapshot` already writes a generated header (`# Status:` / `Updated:`). So the fix is a host-computed `Unmerged: N commit(s), M file(s)` line in that header: a fact only the host can compute, delivered on the surface designed for ambient peer state, readable through the `./agent.sh peers <name>` an agent already runs, and requiring no new mechanism, verb, or file. Three constraints shape it. **It is measured only for an agent whose status changed** — this fan-out is the poll cycle's dominant cost, and probing every agent every cycle would add an SSH round trip per agent for a number that had not moved; the consequence is that the position is exactly as fresh as the snapshot carrying it, which is the mirror's contract already and why the line sits beside `Updated:` rather than pretending to be live. **An unmeasurable position is omitted, not zeroed** — an unreachable host or unprovisioned repo yields nothing, and absence reads as "not measured" while a printed `0` reads as "this peer is holding nothing", which is a claim and a wrong one. **It does not attempt the deeper half**: work a peer has landed but not merged exists only in that peer's clone, and that is the boundary working as designed — the intended bypass is the parcel channel, which carries the sender's whole tree, and which agents were already using to route around this blind spot. Rejected: computing it on demand at read time (the agent cannot see peers at all, which is the whole premise); a new `position` file beside the mirror (a second ambient channel for what is one fact about one agent); and mirroring on position change as well as content change (that is the unconditional probe, reintroduced through the back door).

- **A refusal that names nothing is a refusal that gets cleared**: `./agent.sh rebase` declines on a dirty tree, which is correct — only the agent knows when its tree is at a safe point, and replaying over uncommitted work is how a pre-sync copy silently reverts a peer's landed change. But the refusal was one line with no list, and an agent looking at it beside hundreds of dirty paths does the thing the refusal exists to prevent: clears the tree to get past the blocker. Reported from a clone holding 293 files of delivered content next to 8 of the agent's own. The tool **cannot** answer "which of these are mine" — it cannot read intent, and delivered content and hand-written work are indistinguishable in a working tree — so it answers the question it can: it lists the dirty paths and marks the ones the **incoming base also changes**. That subset is where discarding is not merely lossy but a silent revert of work that already landed, and it is derived (`git diff --name-only HEAD..quimby/base`) rather than guessed. The list is bounded at 20 with a remainder count, because a 300-line dump is as unreadable as no list and the count already carries the scale. The general shape: **a guard that blocks an action must hand over enough to take the right one instead**, or the operator routes around the guard — and routing around this one is exactly the failure it was built to stop.

- **A note passed with `-m` is shell input before it is text, so the rule for it lives in the generated tier — and it names `$` and `\\`, not just backticks**: four incidents across three agents lost words out of notes with no error and nothing to notice: a quoted command name eaten out of a bug report, two whole passages out of a review, a status edit silently missing two phrases, and a parcel about a defective instrument with the instrument's name removed. The cause is that `-m "…"` is a double-quoted shell argument, so the shell rewrites `` ` ``, `$` and `\\` **before** `agent.sh` is invoked — there is no tool-side fix, because the text is destroyed one layer above the tool. Three decisions follow. (1) **The rule names the whole expansion class.** The incident that read most clearly as a backtick failure lost the word `PATH`, which `$PATH` explains just as well; a backtick-only rule would be obeyed and still lose words, because `$` looks like harmless prose. (2) **It lives in the generated tier** (`QUIMBY.md` → every agent's `CLAUDE.md`/`AGENTS.md`) plus `agent.sh help`, not in a workspace-local file. The generated tier is identical for every agent, rewritten on every launch _and_ every `quimby sync`, so it reaches in-flight agents without a rebuild and every future project gets it — a hand-edited `.quimby/agents/CLAUDE.md` fixes one fleet and nothing else. (3) **The guidance is graded by length, not by a blanket ban.** Single quotes are correct and cheap for a short literal line (nothing expands inside them); `--note-file`/stdin is the only form safe for arbitrary prose, so it is named as the default for anything longer. Banning `-m` outright would be ignored for one-liners and would make the rule feel like ceremony. Quimby's own vocabulary is backtick-dense — every convention quotes a command name — so notes _about coordination_ are precisely the ones most exposed.

- **`escalatesTo` is an allow-list, not a fan-out — escalation stays one blocker, one owner**: escalation defaults to the inverse of `directs` (any agent that directs you), but a fleet often wants an upward channel the authority graph doesn't imply — builders that may take a blocker to either reviewer _or_ integration, none of whom direct them. So `escalatesTo` accepts a list (with `@role` slots expanded, like `directs`). The load-bearing choice is what a list _means_: it is the set of agents this one is **permitted** to summon, and the agent names exactly one per `escalate` — it is never a broadcast that wakes them all. Fan-out was rejected on both counts the courier model cares about: waking N supervisors for one question is exactly the token cost the design refuses everywhere else (it is why broadcast is not a handoff mode), and it dissolves ownership — three agents wake, three answer, and the builder gets three conflicting directions to reconcile. A permission set keeps the interrupt singular while letting the graph be wide. The asymmetry with `directs` is preserved and is the point: a permitted escalation target gains no authority over the sender, so `escalatesTo: [review1, review2, integration]` lets a builder summon any of them while only `review1` (which declares `directs`) can direct it back. A bare string stays valid — it reads as a one-element list, so existing config and state need no migration.

- **Headless = detached tmux + nudge; `start`/`stop` bracket it**: the headless mode fell out of two pieces already built. A tmux session can be created **detached** (`new-session -d`) — running but attached to no terminal — and `nudge` can already type into a session by its stable UUID. Detached session + nudge _is_ headless execution: the entrypoint runs unattended and picks up work when woken, no terminal held. So `quimby start` is `run`'s launch with `-A -d` instead of an attach (the `-A` keeps it **idempotent** — starting an already-running agent is a no-op, never a second session), and `quimby stop` is `tmux kill-session`. `start` shares `run`'s whole launch path (SSH sync + lazy init, runtime spec, bundled tmux config) via a common `launch` helper, differing only in attach-vs-detached. Because a detached session is inherently a tmux session, `start` **enrolls a local agent into tmux** (persists the `tmux` flag) if it wasn't — otherwise `run`/`nudge`/`list` wouldn't recognize the session it just made. `stop` warns before killing an **attached** session (a client is in `run`), and both commands are no-op-safe (start-when-running, stop-when-stopped just report). The durable work is on disk (`assignment.md`, the repo), so `stop` only ends the process — never the work.
- **The recovery loop follows the newest wake-up before saved state**: `status.md` is an agent's handoff to its own successor, but it is fallback context rather than an unconditional first read. A bare continuation or `quimby · resume from @status.md` reads status and assignment; `quimby · assignment updated` reads the assignment; `quimby · parcel <name> from <agent>` opens that exact parcel first. This routing prevents a freshly cleared worker from auditing or re-testing a completed stale assignment before it has even read the supervisor parcel that woke it. Parcel nudges carry the content-derived name so the first command is deterministic and costs no inbox search.
- **The agent keeps `assignment.md` current from newer user intent — direct or explicitly relayed**: if the user retasks an agent by typing into its live session, the agent rewrites its assignment so a later reset cannot relapse. A host-stamped user-directed parcel is read first and persisted when the recipient is idle, done, or freshly reset; active direct-user work is preserved until the user resolves the conflict. Ordinary peer notes remain advisory. Writes stay quiet.
- **`list` shows live session state, probed from tmux**: the roster reports each agent as **running** (a detached headless session), **attached** (a client is in `quimby run`), or **stopped** (no session) — read straight from tmux's `#{session_attached}` count, the source of truth, not from any stored flag. Crucially the probe **gates on `has-session` first**: `display-message` against an unknown target silently falls back (empty output, exit 0) whenever the quimby tmux server is up for _other_ agents, so without the gate a stopped agent would misreport as attached. A local non-tmux agent has no session to probe and reads as stopped even while a foreground `run` is live — an accepted limitation, since a foreground agent is one the user is already sitting at and there is no detached session to wake or kill.
- **Aggregate remote status is bounded, not exact-at-any-cost**: `list` and the status overview are scanning surfaces. They should not hang behind a dead VPN, sleeping SSH host, or wedged remote tmux server. Remote probes for session state, pending work, and sync status are therefore bounded by `QUIMBY_REMOTE_PROBE_TIMEOUT_MS` (default 5 seconds; `QUIMBY_REMOTE_STATUS_TIMEOUT_MS` is accepted as an alias). A timeout uses the same conservative fallback as an ordinary probe failure (`stopped`, no work summary, no behind count) and marks the row with `remote timeout` so the user knows the absence of detail is a probe failure, not a clean state.
- **The session transcript is written by the pane itself, via `pipe-pane`**: tmux scrollback is bounded (`history-limit`) and dies with the session, so a durable record needs a file. Rather than bolt a separate logging step onto `run`/`start` (whose attach is a blocking call, awkward to sequence a post-create `pipe-pane` around), the launch **shell command the pane already runs** — the one that does `rename-window` — also runs `tmux pipe-pane -t "$TMUX_PANE" 'cat >> session.log'`. Targeting `$TMUX_PANE` needs no session lookup, and because the command runs once per pane lifetime (fresh session or respawn) it opens the pipe exactly once for both the attached (`run`) and detached (`start`) paths, with no extra tmux round-trips. `quimby log --follow` then `tail -f`s the file. Local agents only for now — an SSH agent's transcript lands on the remote host, which the follow path doesn't yet reach.
- **Transport abstraction**: All agent I/O goes through `LocalTransport` or `SSHTransport`. Commands don't need to know where an agent lives — they call `transport.exec`, `transport.writeFile`, `transport.rsyncTo`, etc.
- **Transport never commits**: Work is captured from the agent's working tree (committed + uncommitted + untracked) via a throwaway index, so `handoff`/`dispatch`/`sync` never make a commit in an agent — frequent use never litters its history, and agents needn't use git at all. The only commit is the optional one at `merge`, the boundary.
- **Three levels of "catch up"**: `sync` keeps the agent's work (delivering the base as `quimby/base`, and applying it only when applying is not a rewrite — see the deliver-vs-apply entry below); `sync -f` drops the work but keeps the agent (mailbox intact); `rebuild --force` recreates the agent (mailbox cleared). `sync -f` resets the code; `rebuild` resets the agent. Destructive levels require an explicit flag.
- **The safe sync fails fast on a pre-wedged repo, and never swallows a failed rebase-abort**: the safe (work-preserving) sync opens by auto-stashing the agent's changes — but `git stash` flatly refuses when the repo is **already** mid-conflict (an in-progress merge/rebase, or unmerged index entries), dying with a cryptic `<file>: needs merge`. That is exactly the confusing failure the courier model should absorb, so `runSyncAlgorithm` probes `pendingConflictState()` **before** the stash and, when the repo is wedged, throws an actionable `QuimbyError` instead — naming what's blocking (merge / rebase / unmerged), the on-agent undo (`git merge --abort` / `git rebase --abort`), `-f` as the hard-reset escape hatch (it resets, clearing the state, so it deliberately skips the gate), and a **ready-to-paste `quimby nudge`** to wake the agent to resolve it. The nudge is offered, never auto-fired: sync surfaces the choice, mirroring `assign`'s "don't wake an agent on a broken baseline." Relatedly, the rebase-conflict recovery used to `rebaseAbort().catch(() => {})` — a swallowed abort failure is precisely how a repo gets left mid-rebase and then wedges the _next_ sync, so `rebaseAbort()` now returns whether it actually cleared the rebase; a failed abort is reported **loudly** (`… the automatic abort failed — its repo is left mid-rebase`) with the same resolve-or-`-f` guidance, and the stash is only popped when the abort succeeded (popping onto a still-conflicted tree would compound the mess). One detection contract (`pendingConflictState`) and one boolean-returning `rebaseAbort` drive both the local git-CLI and SSH-over-transport backends, tested against the fake.
- **`sync` re-renders the agent scaffold — the non-destructive path for a quimby upgrade to reach in-flight agents**: the Quimby-tier scaffold (`CLAUDE.md`/`AGENTS.md` + the `agent.sh`/`.cmd` tool) is regenerated on **every launch**, so a `run`/`start`/`restart` already ships newer docs to an agent. But that coupling only helps agents you relaunch: a `run` re-attaches (and a `start` on a running agent early-returns without rewriting), and the only launch path that both rewrites _and_ takes effect is `restart`, which **reboots** — dropping the live session's context. That leaves a real gap after a `quimby upgrade` with agents in-flight: no way to push the new docs to a running fleet **without killing their sessions/sandboxes**. `sync` fills it, because `sync` is already the verb that iterates agents non-destructively (`--all`), drives both local (git CLI) and SSH (over transport) clones, and touches **neither the tmux session nor the sandbox**. So every `syncAgent` now also calls the same `writeAgentInstructions`/`writeRemoteAgentInstructions` primitive a launch uses, after advancing the base. Three properties make this safe and honest: (1) it rewrites **only generated files** — never `assignment.md`, `status.md`, or the mailbox — so an agent's task and journal survive (the `writeAgentInstructions` split already excludes them; `writeAgentScaffold`'s mailbox/idle-state writes are _not_ reused here); (2) it is **best-effort** across all three sync behaviors (safe/`-f`/`--base`) — a write failure never fails the sync, mirroring the mailbox-prune GC folded into the same spot; (3) it makes the file **current on disk without forcing a reboot** — the running agent ingests it at its next context reset (`/clear` or a fresh instance), because neither Claude nor Codex re-reads its instruction files mid-session. This is deliberately the division of labor between `sync` and `restart`: `sync --all` is the **session-preserving** refresh (docs ready for the next reset, work + context kept), `restart` is the **reboot-and-apply** path (fresh process on current config, resuming from `status.md`). Folding it into `sync` rather than adding a `start --all`/new verb keeps the surface small and reuses the one command whose whole job is "bring agents up to date." The runtime hint passed to the render is the agent's stored default (not a full config resolution) — a later launch re-renders with the fully-resolved runtime, so an approximate value self-corrects, exactly as the launch-time regen already tolerates.
- **Rebuild empties the mailbox in place — inode-stable, never `rm -rf handoff`**: `rebuild` clears the mailbox, but it removes the parcels _inside_ each tray while keeping the tray directories (and `handoff/in`/`handoff/out` above them) as the **same inodes**, rather than deleting `handoff/` and recreating it. The motivation is a real failure hit in the field: an agent's root is frequently a virtiofs/9p guest bind-mount, and replacing the `handoff/{in,out}` inodes host-side leaves the guest holding a **stale dentry** — the directory still lists via `getdents` but every `stat` returns `ENOENT` (and does _not_ self-heal on repeated lookup; only a root `drop_caches` clears it), so the agent's next `mkdir -p handoff/out/draft/<recipient>` fails and it cannot stage a single handoff. Keeping the inodes stable closes the window by construction. Two backstops sit around it, deliberately layered by what each _can_ do: `agent.sh`'s `mkdir` failures print the specific cause + remedy (`sync; echo 2 | sudo tee /proc/sys/vm/drop_caches`) instead of a bare `No such file or directory` — an honest diagnostic, **not** a self-heal, because the only in-guest fix needs root the tool can't assume; and the _complete_ fix (mount coherence, e.g. virtiofs `cache=none`) is the sandbox runtime's job, outside Quimby's reach. An `agent.sh` retry-on-ENOENT was considered and rejected: the stale dentry survives repeated `stat`, so a retry would just fail twice while implying it had healed.
- **remove --force confirms and cleans up best-effort — no skip-remote flag**: removal is destructive, so — mirroring `rebuild` — a bare `quimby remove <agent>` only warns and removes nothing; `--force` is the confirmation. `--force` then does the **full** teardown, including the remote `rm -rf` for an SSH agent, but **tolerantly**: if the host is unreachable the remote step fails, and rather than abort, quimby removes the local state entry anyway and warns that the remote wasn't cleaned. This replaces the earlier design where `--force` _skipped_ remote cleanup — which left a reachable SSH agent's remote workspace as cruft and offered no "confirm + also clean the remote" path. Folding both into one tolerant `--force` means the common case (reachable) is cleaned and the escape hatch (unreachable) still works, with one flag and no way to accidentally orphan a reachable remote.
- **Agents are a machine-wide pool, made visible on the shared tmux socket; reaping is manual-first with opt-in auto**: a live agent is a running sandbox competing for one machine, so past a handful the honest model is a bounded **pool**, not a private roster per project. The problem was that nothing _showed_ the pool: `quimby list` scopes to the current workspace, while every quimby session — local or SSH, every project — runs on one shared socket (`tmux -L quimby`), so the machine could be full of live agents no single `list` revealed. `quimby sessions` is the missing cross-project view: it reads the socket and joins each session back to its owning workspace by the names quimby already mints (`qb-<agentId[:8]>`, `qb-dash-<projectId>`, `qbv-<projectId>-<n>`), so classification is pure string work and the _ownership_ half (present-or-not) is what flags an **orphan** — a session whose workspace or agent is gone, which nothing will ever reattach to. It reads from any directory, because the pool is not a property of where you stand. `quimby sessions prune` reaps by idle age (`--idle`) and/or orphan status (`--orphans`), previewing unless `-f`. The reaping model was chosen manual-first (a `sessions prune` verb) with an **opt-in** server auto-reap (`pool.idleTimeout`) rather than always-on, because reaping ends a live _context_ — never the work, which is on disk and resumes from `status.md`, but the session's in-flight state — so it must be asked for. Two invariants bound the danger: an **attached** session is never reaped (a human is in it), and auto-reap is **scoped to the server's own project** (so two servers on the same socket never fight over each other's pools). The ceiling (`pool.maxLive`) is deliberately **warn-only**: it names the idlest sessions and the prune command at launch but never refuses, because a hard stop mid-workflow is worse than the resource pressure it prevents — a budget you set for yourself, not a lock. Both keys count sessions across **every** project, since that is what actually competes for the machine. Rejected: keying the pool on stored state (the socket is the source of truth — a crashed CLI leaves state stale but the session real); auto-reap on by default (surprises a live context); refusing a launch past the ceiling (turns a budget into a wall). The inventory/prune/capacity logic is its own `@quimbyhq/pool` package (over `@quimbyhq/session`'s `listQuimbyTmuxSessions`/`killQuimbyTmuxSession` socket primitives), so both the CLI and the server's auto-reap share one implementation.
- **`disable`/`enable` are the pool's middle rung — free the session, keep the disk**: the fleet's binding constraint is live sessions (sandboxes/tmux), not disk, so a state was missing between `stop` (transient — a stopped agent is still placed and relaunches next `run`) and `remove` (destructive — clears disk). `quimby disable <agent>` sets a persistent `AgentState.enabled: false` and kills the session, keeping the repo/mailbox/assignment/status; `enable` clears it. The load-bearing half is that the **layout planner prunes disabled leaves** — drops them, collapses an emptied pane, and errors only if _every_ placed agent is disabled — so `quimby run` on a saved layout opens exactly the enabled set **without editing the `expr`** ("disable one without redoing the whole layout"). Absence of the flag means enabled (purely additive), and `list` shows `⊘ disabled` (distinct from the transient `stopped`). It composes with `pool.maxLive`: disabling is how you stay under a session ceiling without discarding an agent.
- **No artificial simplicity**: This is infrastructure for multi-agent orchestration. Networking, servers, persistent state, SSH transport, and status mirroring are all in scope.
- **The multi-panel dashboard is a three-layer nesting of views over retained sessions**: `quimby run "a b | c d"` arranges agents into split panes, each pane itself a tabbed view. Rather than invent a new sharing primitive, this composes the two tmux facts quimby already relies on — a **session** is the unit of retention, and `link-window` is the unit of sharing — into a strict hierarchy: (1) each **agent** is its own long-lived session (unchanged); (2) a **tab group** (`a b`) is an _ephemeral_ session that `link-window`s those agents' windows, i.e. exactly today's tabbed dashboard; (3) a **pane layout** (`|` `/`) is an _ephemeral_ wrapper session whose single window is split into panes, each pane running a nested `tmux attach` to a tab-group session. So a panel dashboard is an ephemeral view over ephemeral views that bottom out in the retained agent sessions — nothing durable is created, and tearing the whole thing down never touches an agent. The grammar is three layout operators over agent names, precedence tightest→loosest: **space** = tab together in one pane, **`/`** = stack rows, **`|`** = columns; parens override. So `a b | c d` is `(a b) | (c d)` — tabs{a,b} beside tabs{c,d} — and `((a b)/c)|d e` is a left column of tabs{a,b}-over-`c` beside a right pane of tabs{d,e}. A trailing **`:N`** on an agent name or a `)` group close is a **size weight** (see the weight decision below): `(a b):70 / c:30` splits the rows 70:30. Bare `quimby run a b` (no operators) stays the flat tabbed dashboard; the panel path engages only when a layout operator is present, so the feature is purely additive. A **host shell** is a slot like any other, written `host` or the shorthand `$`, and — unlike the flat dashboard's single auto-prepended host tab — it is **repeatable**: `$ | $` is two host panes, `a $` is agent `a` beside a host tab, so you can have as many host terminals as you place. A leaf can also be a **`@role` slot** that expands to every instance of a role, tabbed into one pane (see the role-slot decision above); bare names stay concrete-agent references, so the grammar's leaf kinds are: bare = agent, `@role` = role slot, `$name` = service, `$`/`host` = shell.
- **The VS Code extension is a Quimby frontend, not a CLI wrapper**: the desired VS Code experience is a first-class Quimby extension that activates on `quimby.yaml`, starts Quimby's coordination service while the workspace is active, shows a Quimby Home/control surface when no layout is open, restores the user's last layout, opens named side-by-side agent terminals, and closes the whole layout as one group. Shelling out to a global `quimby` binary for everything would make the extension feel bolted on and create install/version friction. The better boundary is shared package APIs: move layout parsing/planning out of `apps/cli`, use `@quimbyhq/server`'s `startServer` directly where practical, and let both CLI and extension call the same core. A JSON layout command is still useful for inspection and third-party tools, but the extension should not depend on it as its main integration path. The extension still should not parse the layout grammar, merge layered config, resolve presets, infer missing agents, or understand host/service tokens on its own; duplicating those rules would create a second source of truth. VS Code can create named terminals and split one terminal beside another, so it can reproduce the common dashboard cockpit well, but weights like `:70` remain best-effort hints and exact weighted pane fidelity stays with the tmux renderer. tmux remains the retained session substrate; VS Code is another viewport and control plane over it.
- **Pane sizes are node weights (`:N`), never percentages, and never touch tabs**: a dashboard node can carry a trailing `:N` — `agentName:N` or a `)` group close `(…):N` — that sets its share of the split it sits in. The `:` sigil is load-bearing: without it a bare number would collide with the `space = tab together` rule and parse as a tab member named `N` (agent names are arbitrary strings, digits included), and it visually binds the size to the **node** rather than burying it among a pane's contents — a size is a property of the panel, not of what's tabbed inside it. Weights are **relative** (sum-and-divide), not percentages: siblings need not total anything, unsized siblings split the remainder equally (`a:70 / b / c` → b and c share the leftover 30), and the model composes cleanly under nesting where a fixed-100 rule would not. A `%` sigil was rejected for implying a must-total-100 that weights don't have. A weight is only meaningful on a node that has siblings under a split axis (`|` or `/`); a weight on a lone pane or on a **tab member** (`(a:2 b:1)` — tabs have no size, only one shows at a time) is an **error**, surfaced rather than silently dropped, so the grammar tells you sizes don't apply to tabs instead of quietly ignoring the `2:1`. The ratio model deliberately mirrors tmux's own percentage-based pane resize, so the wrapper can map weights straight onto pane sizes.
- **The panel wrapper grabs no key binds; the tab layer owns the prefix**: tabbing is the high-frequency action, so `C-b` must reach the _tab_ layer, not be consumed by the pane wrapper. The wrapper session is created with `prefix None` — it never enters prefix mode, so `C-b` passes straight through to the focused pane's nested client (the tab group) where it drives tab switching. Pane management (the rarer op) lives on no-prefix root-table chords (`bind -n M-Left/Right/z`) plus `mouse on` (click-to-focus, drag-to-resize). One prefix to learn, doing the frequent thing. A consequence that falls out cleanly: `C-b d` in a pane detaches that pane's inner client, which (via the teardown below) collapses the whole dashboard — so the detach reflex becomes "cleanly leave the dashboard," agents surviving. This supersedes an earlier two-prefix scheme (`C-Space` for panes) as both simpler and better-aligned with how the dashboard is actually used.
- **Ephemeral views bubble-up teardown; any exit collapses the group, agents survive**: the ephemeral sessions of one dashboard invocation share a name prefix (`qbv-<projectId[:8]>-…`); the agents are a separate namespace. Each pane's command is `tmux attach -t <view>; <teardown>`, so when any child dies or is detached its attach returns and the teardown collapses the entire group — making orphaned views structurally impossible (the failure mode of a top-level-only GC). Two non-obvious requirements, both learned from a prototype and easy to get wrong: the teardown must run **detached on the tmux server** (`run-shell -b`), not inline in the doomed pane, or it kills its own host shell mid-sweep and leaks the siblings; and it must kill the wrapper session **last**. Because agents are retained, an aggressive "any exit collapses the viewport" default is the right one — re-running the dashboard is instant — rather than a gentler per-pane close. A separate, non-obvious nesting requirement: a pane running `tmux attach` inherits `$TMUX` and tmux refuses to nest, so the pane silently dies unless the command clears it (`sh -c 'TMUX= tmux … attach …'`).
